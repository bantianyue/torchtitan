local_map 是什么 · 在哪儿用

torchtitan 声明式并行（declarative sharding）中的「本地计算区」机制 —— DTensor 边界与原语，源码基于 D:\02_source\torchtitan

① 一句话定义

local_map（PyTorch torch.distributed.tensor.experimental.local_map）把一个只接受普通本地张量（plain tensor）的函数包成一个可接收/产出 DTensor 的函数：

前向： DTensor 输入 → (边界) 按 in_placements 取本地分片 → 在本地张量上执行 fn（无 DTensor 分发） → (边界) 按 out_placements 包回 DTensor 输出
反向： 输出梯度 → 按 out_placements 反推本地梯度 → 在本地执行反向 → (边界) 按 in_grad_placements 包回 DTensor 输入梯度

在 torchtitan 里，它就是 ShardingConfig.local_map（protocols/sharding.py:108-119）声明、Module.parallelize() 施加的「forward 包装」：输入重切分 → [local_map 本地计算] → 输出重切分（protocols/module.py:248-294）。

② 它解决什么问题（为什么需要它）

1. 跑不了 DTensor 的算子也能并行

很多算子/内核不支持 DTensor 分发：FlexAttention、自研 CUDA kernel、grid_sample、F.interpolate、高级索引（scatter/gather）、Conv1d 等。用 local_map 把 DTensor 在边界「卸」成本地张量，函数体照常写普通张量代码，并行语义由边界的 placements 声明。

2. 通信位置显式化、可控

所有需要的 all-gather / reduce-scatter 都发生在 local_map 边界（由 in/out placements 驱动），函数体内零通信。比如 GQA 内注意力的 k/v 在 CP 轴 all-gather 到 Replicate、行并行输出 Partial 归约，都在边界一次完成，语义清晰。

3. 性能：省掉 DTensor 算子分发开销

函数体在本地张量上跑，没有逐算子 DTensor placement 匹配与规约的开销；且本地张量区域对 torch.compile 更友好，局部逻辑（如 MoE 的 token dispatcher、融合 SwiGLU kernel）可以被编译器整段优化。

4. 反向梯度布局一并声明

in_grad_placements 保证反向时输入梯度按正确布局回流（如行并行权重的梯度来自 Partial 输入梯度的归约、CP 下 k/v 本地梯度以 Partial 累积再在边界归约），避免手写梯度通信。

⑤ 重点拆解：GQA 内注意力（最典型用法）

# models/common/decoder_sharding.py:190-229
def set_gqa_inner_attention_local_map(inner_attention_cfg):
    q_placements    = dense_activation_placement(tp=S(2))                      # 头维 TP 切分
    kv_src_placements = dense_activation_placement(tp=S(2))
    kv_dst_placements = dense_activation_placement(tp=S(2), cp=R)               # CP 下 k/v all-gather 成 Replicate
    kv_grad_placements= dense_activation_placement(tp=S(2), cp=P)               # 反向 k/v 梯度 Partial 累积
    inner_attention_cfg.sharding_config = ShardingConfig(
        in_dst_shardings={ "q_BLNH": q_placements, "k_BLNH": kv_dst_placements, "v_BLNH": kv_dst_placements },
        out_src_shardings=q_placements,
        local_map=LocalMapConfig(in_grad_placements=(q_placements, kv_grad_placements, kv_grad_placements)),
    )
  • 为什么这里需要 local_map：FlexAttention / SDPA kernel 不在 DTensor 分发支持范围内（或按 local 实现性能更好），且 q/k/v 已是头维切分的 DTensor —— 在边界卸成本地，kernel 直接消费本地分片。
  • CP 叠加：k/v 的 in_dst 是 CP 轴 Replicate，local_map 边界自动 all-gather 全长 K/V；q 保持 CP 切分 —— 一套声明同时表达 TP + CP 两层并行。
  • 反向：in_grad_placements 让 q 梯度保持 seq 切分、k/v 梯度以 Partial 累积后在边界归约，梯度布局与正向完全对称。

⑥ 注意事项

① 顺序约束：CP 包装（apply_cp_to_forward）必须在 parallelize() 之前调用；否则 CP 逻辑跑在 local_map 边界外，拿到的是 DTensor 而非本地张量，直接出错（context_parallel/api.py:41-42、llama3/parallelize.py:47-54 注释）。
② 声明完整性：设了 local_map 就必须有 in_dst_shardings（覆盖 forward 全部位置参数，否则 _maybe_wrap_with_local_region 抛 AssertionError）和 out_src_shardings（module.py:435-445）。
③ 非张量参数：非张量参数在 in_grad_placements 里用 None 占位（local_map 原样透传），mesh 解析时会被过滤（module.py:469-471）；MoE 里路由元数据（num_local_tokens_per_expert_E）虽是元数据仍是 DTensor 输入，也必须给 placement（moe_sharding.py:256-259）。
④ 双后端：DTensor 后端用 torch.distributed.tensor.experimental.local_map（placement 元组），spmd_types 后端用 torch.distributed.tensor.experimental.spmd.local_map（in_types/out_types 字典），二者由 parallel_dims.spmd_backend 选择，别混用。

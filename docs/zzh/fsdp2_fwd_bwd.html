1. 先建立心智模型：FSDP2 到底“动”什么

FSDP（Fully Sharded Data Parallel）的思想是：权重、梯度、优化器状态这三样，都只在一部分 DP rank 上各存 1/DP 份。 torchtitan 的 full_dtensor 模式下，这份“分片”用 DTensor Shard(0) 表示；TP/CP 造成的那部分切分在 Module.parallelize() 阶段已经做完，FSDP 只负责数据并行轴上的分片与恢复。

因此 FSDP2 每轮训练反复做三件事，理解 fwd/bwd 只需要这三件事：

动作方向做什么发生在哪
unshard 分片 → 完整 发起 all-gather，把各 rank 手里的 1/DP 份拼成完整参数；完整副本放在 all-gather 输出 buffer 里 Pre-Forward、Pre-Backward（反向要再算一次梯度，所以前向结束后释放过的话，反向要重新恢复）
reshard 完整 → 分片 释放完整参数 buffer，把模块属性重新指回 sharded 参数，省显存 Post-Forward（可选）、Post-Backward
reduce-scatter 梯度 完整梯度 → 本地分片梯度 把完整梯度跨 DP rank 求和后，每个 rank 只留下属于自己那 1/DP 份（HSDP 时先沿 replicate 轴 all-reduce） Post-Backward
关键前提 反向传播不会“自动知道”参数现在是不是完整的。torchtitan 只是把每个 TransformerBlock 交给 fully_shard()，让 FSDP2 用“围绕模块 forward/backward 的钩子”在正确时机执行上表的动作——这就是本文要讲清的 fwd/bwd 流程与原理。

2. 一个参数组的 fwd/bwd 生命周期（图 1）

先固定符号：下面图里 W 指“当前这个 block（FSDP 参数组）的全部模型参数”，例如 attention 的 q/k/v/o 和 FFN 的 weight；∂L/∂W（或简写 grad）指这些参数的梯度。凡是 all-gather，通信的都是“W 的 1/DP 分片”； 凡是 reduce-scatter，通信的都是“完整梯度 ∂L/∂W”；reshard 只是本地释放显存，不是集合通信。 图 1 把“一个 FSDP2 参数组”（dense 场景下 = 一个 TransformerBlock）在一轮训练里的状态变化串起来： 蓝色是 forward 阶段（自左向右），橙色是 backward 阶段（自右向左，与计算图逆向一致）。

图中的通信通信的是“什么”方向 / 结果
② all-gather（unshard） 本 block 参数 W 的 1/DP 分片（weight 张量，不是激活、不是梯度） 每个 rank 把分片发给全体 → 每 rank 得到完整 W，供 forward 计算
⑤ all-gather（unshard） 同样是本 block 参数 W 的分片 forward 完已 reshard，反向要算梯度前再恢复完整 W
⑤ 里的 prefetch “前一个 block（forward 顺序上相邻）”的参数 W 分片 提前发起它的 all-gather，等轮到它反向时往往已 ready
⑦ reduce-scatter 本 block 的完整梯度 ∂L/∂W（不是 W） 跨 DP rank 求和后，每 rank 只留属于自己的 1/DP 梯度分片
注意 ⑤ 与 ④ 的区别 若 reshard_after_forward=True（dense + 无 PP 的默认值），④ 已经把完整参数 W 释放，所以 ⑤ 必须 对参数 W 再 all-gather 一次才能供反向计算梯度。torchtitan 对最后一组（norm+lm_head）和 FSDP 根模块会刻意少做这次释放， 因为“释放后马上又会被 prefetch/再用”不划算。

3. Forward：unshard → 计算 → reshard → 挂输出 hook

torchtitan 不会自己实现这些钩子，它只按模块粒度调用 fully_shard()（见第 7 节）。hook 骨架在 PyTorch FSDP2： fully_shard() 初始化时给模块注册一次 forward pre-hook 与 forward hook （_fsdp_state.py:105-130）。这两层钩子不是“每轮现挂”，而是 “注册一次、每轮 forward 都会触发”。

3.1 Pre-Forward（模块 forward 之前）

  • 第一次进入时做 lazy init：确定 FSDP 根、共享通信流、初始化所有参数组。
  • 每个参数组执行 pre_forward()：unshard()（all-gather）→ wait_for_unshard()， 把参数恢复到完整状态（_fsdp_param_group.py:550-568）。
  • 本轮第一次进入 forward pass 时，把 RegisterPostBackwardFunction 这个自定义 autograd 节点包到 模块输入里 requires_grad 的张量上（同段代码 567 行调用 _register_post_backward_hook(args, kwargs)， 实现在 _fsdp_param_group.py:917-934）。

3.2 模块真实 forward

参数已经完整，attention / FFN / 归一化等真实算子正常执行；autograd 图在这段计算中被构建。 full_dtensor 下输入输出都是 DTensor，但这不影响 FSDP2 的流程。

3.3 Post-Forward（模块 forward 之后）

  • 参数组执行 post_forward()：若 reshard_after_forward 为真，立即 reshard 释放完整参数， 并记录一次 post_forward_order（作用见下，供 backward 默认 prefetch 使用） （_fsdp_param_group.py:570-583）。
  • FSDPState 随后调用 _register_pre_backward_hook(output)：从输出结构里收集 requires_grad 的张量， 对每个张量执行 t.register_hook(self._pre_backward) （_fsdp_state.py:328-344 与 :440-466，register_hook 在 458 行）。
记录 post_forward_order 是干什么的 post_forward_order 是 FSDP2 每个训练迭代里、按“各参数组 forward 完成的先后”记录的一张顺序表： dense 场景下大致是 [block0, block1, ..., norm/lm_head]。它的唯一用途是给默认 backward prefetch当“调度表”。 反向时参数组按 forward 的逆序被使用，所以当第 i 个组的 Pre-Bwd 触发时， _backward_prefetch() 会从 post_forward_order 取第 i-1 个组， 提前对它发起参数 all-gather——这样等上一层的梯度真到输出时，参数往往已经就绪，只差 wait （实现见 _fsdp_param_group.py:821-857）。 如果 torchtitan 显式调了 set_modules_to_backward_prefetch（MoE+EP 路径），就改用显式列表，不再走这张默认表。
为什么 Pre-Bwd hook 要“每轮 forward 后”挂 autograd hook 是挂在张量上的，而每次 forward 都会产生全新的输出张量。只能在张量刚诞生、还在计算图里时把 hook 挂上， 反向梯度流经它时才能拦截到“本模块的参数马上要被求梯度”这个时机。

4. Backward：Pre-Bwd 重新 unshard → 算梯度 → Post-Bwd reshard + reduce-scatter

反向不是“FSDP 自己从头再跑一遍 forward”，而是 autograd 沿着 forward 构建的计算图逆向执行。 FSDP2 只在图的边界安插触发器，让参数在需要时是完整的、用完立刻被释放。

4.1 Pre-Bwd Hook 触发（模块反向开始前）

loss 的梯度沿图回流，到达本模块 forward 时产生的输出张量时，_pre_backward(grad) 被调用 （_fsdp_state.py:386-399）：

  1. 训练状态置为 PRE_BACKWARD，并注册 root 级“最终收尾回调”（防止某些参数组漏掉 Post-Bwd）；
  2. 每个参数组执行 pre_backward()：unshard() + wait_for_unshard()。 这里 unshard 的是本参数组的参数 W（再次 all-gather W 分片），不是梯度。 若该组参数已被 prefetch（all-gather 已发出、只差等待），这里就是 no-op（_fsdp_param_group.py:592-605）；
  3. 随后按需 prefetch：默认实现 _backward_prefetch() 取 post_forward_order 中“forward 顺序上一个”的参数组， 也就是前一个 block 的参数 W（不是梯度），提前把它的 all-gather 发出去（:821-857）；若 torchtitan 在 MoE+EP 下用 set_modules_to_backward_prefetch 指定了显式列表，则改 prefetch 显式指定的 block。

4.2 模块内部反向计算

autograd 逆序执行本模块内的算子，完整参数上产生梯度，先累积到 unsharded 参数（或 unsharded_accumulated_grad）。 这段不需要 FSDP 干预——它只保证参数此刻是完整的。

4.3 Post-Bwd 触发（模块反向结束后）

反向继续流到“模块输入边”时，4.1 之前插入的 RegisterPostBackwardFunction 的 backward 被执行，调用 ctx.param_group.post_backward()（_fsdp_param_group.py:1141-1163）。 post_backward() 内部（:607-790）：

  1. 若需要，把已计算的梯度累积进 unsharded 梯度状态（:625）；
  2. 取出 unsharded 梯度引用；
  3. reshard 参数（释放完整副本，模块属性指回分片参数）；
  4. reduce-scatter 梯度：跨 FSDP rank 归约后只留本地 1/DP 份（HSDP 时先沿 replicate 轴 all-reduce）。
为什么输入边节点能保证“梯度已经算完” RegisterPostBackwardFunction 位于本模块输入张量上。autograd 执行到它时，本模块内所有算子（也就是会往参数上累积梯度的算子） 的反向都已执行完；它再把自己的 backward 结果（原样梯度）放行给前一个 block。这正是 FSDP2 把“Post-Bwd 触发点”放在输入边、 而不是参数边的原因。

4.4 root final callback 兜底

有些参数组的输入张量 requires_grad=False，autograd 节点不会插入，Post-Bwd 就不会在图中被触发。因此 4.1 注册的 root 收尾回调在整次 backward 结束时，对仍处于 PRE_BACKWARD/FORWARD 状态的组补执行 post_backward()、清状态、等待 reduce-scatter 事件 （_fsdp_state.py:401-438）。

6. 多层训练：prefetch 让 AG / 计算 / RS 重叠（图 3）

真正的训练里有很多个 block。forward 自下而上（0→N-1），backward 自上而下（N-1→0）。 每个 block 被 fully_shard 包成独立 FSDP 参数组后，FSDP2 维护一个 post_forward_order， backward 中 block i 的 Pre-Bwd 一旦触发，就立刻给“forward 顺序上的上一个 block”（即反向顺序的下一个） 发起 prefetch all-gather——这里 prefetch 的是那个 block 的参数 W_{i-1}，不是梯度： 让 AG W_{i-1} 和 block i 的反向计算重叠。等 block i-1 的梯度真到输出时，它的参数往往已经 prefetch 完，只差 wait。

7. 对应回 torchtitan：full_dtensor + 每 block 一个 fully_shard

full_dtensor 是一种“所有参数/输入都是多维 SPMD 网格上的 DTensor”的后端。数据并行只是其中一部分： FSDP 通过 DataParallelMeshDims(shard=..., replicate=...) 被告知哪些轴归自己管 （full_dtensor.py:70-107）。

torchtitan 位置做什么与本文流程的关系
parallelize.py:43-50 full_dtensor 下先 model.parallelize(parallel_dims) TP/CP 分片和输入输出重分布在这里完成，参数成为多维 DTensor
parallelize.py:69-88 调 apply_fsdp_to_decoder() 并传入 dp_mesh / dp_mesh_dims 把“哪些轴是 FSDP 数据并行轴”传给 fully_shard
distributed/fsdp.py:238 每个 dense TransformerBlock 一次 fully_shard(...) 每个 block 成为独立 FSDP 参数组——第 4/6 节的“一个组 = 一个 block”
distributed/fsdp.py:200-206 最后一组 norm+lm_head 默认不 reshard_after_forward 避免“释放后马上被 prefetch”的浪费，即 3.3 的例外
distributed/fsdp.py:310 根模型再 fully_shard(model) FSDP 根不负责新增分片组，负责共享通信流与 lazy init/收尾回调
distributed/fsdp.py:326-366 仅 MoE+EP 时用 set_modules_to_forward/backward_prefetch 显式指定 dense 走 FSDP2 默认 prefetch；EP 因 D2H 同步干扰默认策略而改为显式列表
一个常见困惑 “full_dtensor 下参数本来就有 TP/CP 分片，unshard 会不会把它们也 all-gather 回来？”不会。 FSDP2 的 unshard 只针对自己的数据并行 shard 轴；参数完整指的是“沿 DP 轴完整”。本文图中为讲清 FSDP 机制只画了 DP 轴。

9. 常见误解与 FAQ

问题答案（以 FSDP2 代码为准）
Post-Bwd Hook 是挂在 nn.Parameter 上吗？ 不是。register_post_accumulate_grad_hook 是 FSDP1 对 FlatParameter/AccumulateGrad 的做法； FSDP2 的触发点是 pre-forward 插入在模块输入张量上的 RegisterPostBackwardFunction，另有 root final callback 兜底。
为什么 Pre/Post-Bwd 的“挂载”似乎每轮 forward 都要做？ 模块级 forward pre/post hook 只在 fully_shard 初始化时注册一次；每轮要做的是把 autograd 图节点插进 本轮的图（输入边）以及给本轮新的输出张量挂 hook——图和张量都是每轮新建的。
初始化时参数是 sharded 的，会不会“挂错、通信错乱”？ 不会。FSDP2 初始化时参数本来就处于 sharded（甚至 meta/未物化）状态；unshard/reshard 由参数组在 forward 时统一切换。 “必须在参数完整后才能挂 hook”是 FSDP1 式说法，不是 FSDP2 的约束。
reshard_after_forward 对流程影响大吗？ 只影响显存与通信次数，不影响正确性。True = 前向完释放、反向重新 AG（dense 无 PP 默认）；False = 参数保留到反向， 反向 Pre-Bwd 的 unshard 变成 no-op（torchtitan 最后一组/PP 默认等场景）。
激活重计算（AC）会重复挂 hook 吗？ FSDP2 对 PRE_BACKWARD 状态下的重计算 forward 做了特判：跳过 reshard 与重复注册，只做输出 dtype 转换 （_fsdp_state.py:290-344）。
HSDP 与这里讲的有差别吗？ 本文按纯 FSDP 讲。HSDP 多一个 replicate 轴，Post-Bwd 的归约先沿 replicate 轴 all-reduce，再沿 shard 轴 reduce-scatter； hook 挂载位置与 fwd/bwd 时机完全相同。

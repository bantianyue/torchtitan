0三层总览

一句话:torchtitan 决定"怎么切",pytorch 负责"按切法插通信",底层 CUDA/NCCL 负责"真正在 GPU 上把数据搬过去"。三层各管一段,谁也不越界。

① torchtitan 负责"切什么、怎么组装" -- 只写声明,不动任何数据。它告诉你:这个权重切成 8 份、那个专家走另一组、前 3 层是一段后 58 层是一段。产出是一份"切分方案"(配置树 + 调用顺序),不产生任何一次通信、不搬动一个张量。它甚至不知道 NCCL 是什么。

② pytorch 负责"把切分方案变成运行时动作" -- 真正开始动数据。eager 下只做"对的事":在 forward 的正确位置插入 all-gather / reduce-scatter / 点对点传输,让切开的张量在正确时刻拼回 / 拆开,通信逐个调用、不重叠、不融合;compile 时 Inductor(属 PyTorch)再把通信与 matmul 融合重叠做"快的事"。它既保证算得对,compile 时也兼顾算得快。

③ CUDA & NCCL 负责"把通信真正执行掉" -- GPU 上真正收发数据的是这一层。NCCL 启动 ncclAllGather 等内核做多卡通信,CUDA 提供 stream 与执行环境。它只执行不编排(通信-计算融合由 ② Inductor 做),只认内核、不懂模型语义。"收发够不够快"由这层决定。

举个同一件事穿过三层的例子(一次参数 all-gather,即 FSDP 把切开的参数拼回完整):

层这一层对"all-gather"做了什么有没有真搬数据
① torchtitan写一行声明:weight: {fsdp: S(0)}(这权重在 fsdp 组上切第 0 维)。仅此而已。没有。只是个标注。
② pytorchforward 开始时触发一个 hook,对这权重调 all_gather 把各 rank 的切片拼回完整参数,供计算用;compile 时 Inductor 把这次 all-gather 融进 matmul 做重叠。有;eager 单独调用串行,compile 时与计算重叠。
③ CUDA/NCCL启动 ncclAllGather 内核在 GPU 上并行收发(CUDA 提供 stream/执行环境)。只执行不编排。有,GPU 上真正收发。

所以三层不是"同一件事分三遍讲",而是职责递进:① 画图纸(不施工) -> ② 按图纸施工(对;compile 时还把施工编排成流水线做重叠,因为 Inductor 也属 PyTorch) -> ③ 开动 NCCL/CUDA 机器真正执行。下面这张图把每层"实际在干什么"和四策略(FSDP/TP/PP/CP)逐格列清楚。

② 和 ③ 按代码归属分层(纠正:Inductor 属 PyTorch ② 层,不在 CUDA/NCCL 层):

② PyTorch 层 = 全部 torch/ 下的东西,分两个子层:   (2a) 机制层(eager 也走):hook / DTensor.redistribute / schedule--保证算得对,通信与计算串行不重叠;   (2b) 编译优化层(仅 torch.compile 走):Inductor 把 (2a) 插的 _c10d_functional 算子降级成 _CollectiveKernel 图节点,与 matmul 统一调度做通信-计算融合重叠。Inductor 是 torch.compile 默认后端,在 torch/_inductor/(comm_lowering.py、fx_passes/micro_pipeline_tp.py),代码归属 PyTorch。它只产出"调度好的图",不直接调 NCCL。

③ CUDA & NCCL 层 = NVIDIA 的执行环境,纯执行(不含融合):   NCCL(NVIDIA Collective Communications Library)管多卡通信,执行 ncclAllGather/ncclReduceScatter 等内核;   CUDA 管单卡运行时(cudaMalloc / kernel / stream),是 NCCL 与所有 kernel 跑起来的底层。   PyTorch 经 C++ ProcessGroupNCCL(在 torch/csrc/distributed/c10d/)调 NCCL,ProcessGroupNCCL 又依赖 CUDA 运行时。

为何以前把 Inductor 画在 ③?混了"职责归属"(Inductor 决定"快不快",概念上属性能层)和"代码归属"(Inductor 在 torch/ 下,属 PyTorch)。分层应按代码归属划:② 全是 PyTorch 包内(含编译器),③ 是跨语言、跨厂商的 C++ 调 NVIDIA 库。Inductor 产出的图节点最终仍落到 ③ 的 ProcessGroupNCCL -> ncclAllGather -> CUDA 去执行--Inductor 编排,③ 执行。
从 ② 的一次 all-gather 到 ③ GPU 收发数据:完整调用链
② hook: tensor.redistribute(Replicate)
  -> funcol.all_gather_tensor (distributed/_functional_collectives.py)
    -> torch.ops._c10d_functional.all_gather_into_tensor (注册的 C++ 算子)
      |-- ② 机制层(eager): -> dist.all_gather_into_tensor -> [③] ProcessGroupNCCL::allgather -> ncclAllGather -> CUDA stream
      `-- ② 编译优化层(torch.compile): Inductor 降级为 _CollectiveKernel 节点(comm_lowering.py)+ 与 matmul 重叠(micro_pipeline_tp.py),仍 -> [③] ProcessGroupNCCL -> ncclAllGather -> CUDA
② 只编排(机制 + 编译融合),③ 执行(ProcessGroupNCCL -> ncclAllGather -> CUDA stream 收发)

一句话:②(PyTorch,含 Inductor)负责"插通信 + 编排融合";③(NVIDIA CUDA/NCCL)负责"在 GPU 上真正收发执行"。Inductor 属 ② 不属 ③。

用户层与下面三层的关系:用户层是配置输入,不是代码层--它只决定"启用哪些并行、各自几度",本身不产生 ShardingConfig、不挂 hook、不调 NCCL。因此上面的"三层本质对比"表对比的是 ①②③ 三个代码层,用户层作为它们的上游前提不入表(它没有"产出物 / 数据移动 / FX 图节点"这些代码层才有的维度)。各策略(FSDP/TP/PP/CP)章节后面讲"三层实现",指的也是这同一套 ①②③ 代码层(② 含 Inductor 编译优化,③ 是 NCCL/CUDA 执行)。

①torchtitan 层:声明式切分

torchtitan 自己不实现通信。它做两件事:(1) 在 ShardingConfig 里声明每个参数/激活的放置(Replicate/Shard/Partial on 哪个 mesh 轴);(2) 编排"什么时候调 pytorch 的哪个 API"(parallelize_deepseekv3 的调用顺序)。真正的切分由 Module.parallelize() 递归施加。

声明式 ShardingConfig(protocols/sharding.py)

# 一个 ShardingConfig 描述"这个模块进/出/权重怎么放"
@dataclass
class ShardingConfig:
    state_shardings: dict[str, SpmdLayout]   # 权重/buffer 放置(如 weight: {TP: S(0)})
    in_src_shardings: dict[...]              # 入参当前放置
    in_dst_shardings: dict[...]              # 入参目标放置(进 forward 前 redistribute 到此)
    out_src_shardings: SpmdLayout                  # 出参当前放置
    out_dst_shardings: SpmdLayout                  # 出参目标放置(出 forward 后 redistribute)
    local_map: LocalMapConfig | None             # 是否包一个本地计算区(local_map)

Module.parallelize() 把声明施加到树(module.py:248-294)

def parallelize(self, parallel_dims):
    # 1. 递归子模块
    for child in self.children():
        child.parallelize(parallel_dims)
    if self._sharding_config is None: return
    # 2. 按 state_shardings 把参数/buffer 变成 DTensor(distribute_tensor)
    self._distribute_states(parallel_dims)
    # 3. 用 local_map / redistribute 包装 forward
    fn = self._maybe_wrap_with_local_region(self.forward, parallel_dims)
    def forward_with_redistribution(*args, **kwargs):
        args, kwargs = self._redistribute_inputs(parallel_dims, args, kwargs)  # 入参 redistribute(插通信)
        outputs = fn(*args, **kwargs)                                   # 本地 forward
        return self._redistribute_outputs(parallel_dims, outputs)        # 出参 redistribute(插通信)
    self.forward = forward_with_redistribution
① 层的关键:torchtitan 写的全是声明(ShardingConfig 字段)和编排(parallelize_deepseekv3 调用顺序:CP 包装 -> parallelize -> async TP -> AC -> compile -> FSDP)。所有 redistribute / fully_shard / split_module 都是调 pytorch 的 API。① 层不知道 NCCL 存在。

2.4 shard_placement_fn 与 MoE/EP 专家的 FSDP 处理

这是 FSDP 在 MoE 模型里最关键的一步。普通参数和专家参数要分到不同的通信组做 FSDP--普通参数在 fsdp 组上分片,专家参数在 efsdp 组上分片(因为专家还受 EP 切分)。一个模块里两种参数混在一起,怎么让 fully_shard 区分对待?靠 shard_placement_fn:它是个"逐参数分流函数",对每个参数返回"这参数该用哪个 mesh、切哪维"。

shard_placement_fn 是什么

fully_shard 默认把传入模块的所有参数塞进同一个 mesh 做分片。但有时同一模块的参数该走不同 mesh--MoE 层就是典型:专家权重走专家专用组,其余走普通组。shard_placement_fn(param) -> ShardPlacementResult 让你逐参数决定:ShardPlacementResult(placement=Shard(dim), mesh_info=某组 mesh)。FSDP2 的 _init_param_group(fsdp_init.py)按返回的 mesh_info 把参数按通信组分组:同组的进一个 FSDPParamGroup(组内合并通信),不同组分开建 group--所以一个 MoE 层的 FSDPState 下有两个 param group(普通参数组 + 专家组),各走各的通信组。

三个 mesh 的关系(以 192GPU / TP2/SP2/CP4/PP3/EP2/dp_shard8 为例):
· fsdp = dp_shard × cp = 8 × 4 = 32(普通参数的 FSDP 组大小)

# AsyncCollectiveTensor.trigger_wait:1050 -- 第一次被下游算子用时才同步
def trigger_wait(self):
    if not self.completed:
        self.elem = wait_tensor(self.elem)   # torch.ops._c10d_functional.wait_tensor
        self.completed = True
    return self.elem
# __torch_dispatch__:1066 -- 非视图算子触发 trigger_wait(CUDA stream 同步),视图算子不 wait
异步设计:NCCL 内核在通信流上异步启动,返回的 AsyncCollectiveTensor 是"占位"。下游第一次真正用它的值时(matmul 等),__torch_dispatch__ 触发 wait_tensor 同步通信流与计算流。这让通信可以与之前的计算重叠(即便不 compile)。编译时 inductor 进一步把 wait 调度到最优位置。

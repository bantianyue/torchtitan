1. 普通 TP / SP 的通信瓶颈

Tensor Parallelism 把线性层切成 Colwise / Rowwise 两块。为了让 LayerNorm / 激活也分摊到各 TP rank， torchtitan 默认叠加 Sequence Parallel（SP）：激活在层与层之间按序列维切分，只有进入/离开某些线性层时才通信。

位置典型动作语义
进入“需要完整输入”的层（如 colwise 线性前）all-gather 每个 rank 持有序列的一段 [B, L/TP, D]；下游线性层要看到全序列，故拼成 [B, L, D]
Rowwise 线性 / 输出投影之后reduce-scatter 各 rank 算出完整结果的部分和，需要“先跨 rank 求和，再切回序列分片”

在普通写法里，all_gather → wait_tensor → matmul 是串行的：NCCL 把整块数据收齐并 wait 之后， matmul 才开始。通信期间计算单元“空等”，或者更准确地说，通信延迟暴露在关键路径上。tensor 越大、TP 度越高、带宽越紧张，这个问题越明显。

2. Async TP 的核心思想：通信-计算微流水线

把 all-gather 想成“从 P 个 rank 各收一块 A_i”，而 A_full @ B 可以按行分块并行算：

数学直觉（all-gather 沿序列/首维） A_full = [A_0; A_1; …; A_{P-1}]（沿 gather dim 拼接），那么 A_full @ B = [A_0@B; A_1@B; …; A_{P-1}@B]。 所以不必等 P 块全部到齐再算：每收到一块 A_i，立刻计算 A_i @ B 的对应输出行。

把“一整块 all-gather”切成许多小块后，通信与计算按“小块”交替，形成 micro-pipeline。计算流和通信流上的活动交错： rank 0 的通信还没结束，前面已到达的块已经开始做 matmul。all-gather 的尾部延迟、以及 reduce-scatter 的尾部，都可以被计算遮住。

3. TorchTitan 接入：一个开关与一次调用

TorchTitan 侧的 Async TP 代码非常少：配置里一个开关，parallelize 时一次调用。真正实现完全在 PyTorch。

# config/configs.py:137
enable_async_tensor_parallel: bool = False

# distributed/tensor_parallel.py:102-115 —— 全部“接入代码”就这些
def maybe_enable_async_tp(parallelism, compile_config, tp_mesh):
    if not parallelism.enable_async_tensor_parallel:
        return
    if not (compile_config.enable and "model" in compile_config.components):
        raise RuntimeError(
            "Async TP requires 'model' in --compile.components and --compile.enable")
    torch._inductor.config._micro_pipeline_tp = True   # ← 关键动作：打开 Inductor 内部开关
    logger.info("Async TP is enabled")

各模型的 parallelize.py 会在“声明式 TP/EP 并行化之后、torch.compile 之前”调用它：

# models/deepseek_v3/parallelize.py:53  / models/llama3/parallelize.py:56
# 顺序：CP 包装 → model.parallelize() → async TP → AC → compile → FSDP
maybe_enable_async_tp(parallelism, compile_config, parallel_dims.get_mesh("tp"))

仓库里的典型配置是 Llama 3.1 405B（llama3/config_registry.py:317-320）：

parallelism=ParallelismConfig(
    tensor_parallel_degree=8,
    enable_async_tensor_parallel=True,
)
为什么必须配 torch.compile？ Async TP 需要 Inductor 在 FX 图上做“all-gather → matmul”的模式替换，而模式匹配只发生在 torch.compile 的编译图里（eager 模式没有这张图）。maybe_enable_async_tp 因此强制要求 compile.enable=True 且 compile.components 含 "model"。 qwen3_5 还在自己的 parallelize 里显式再检查一次（qwen3_5/parallelize.py:66）。

4. PyTorch 实现：Inductor 模式匹配

在 torch 2.12.1 中，torch/_inductor/config.py:1107 定义了私有开关 _micro_pipeline_tp = False。打开后，Inductor 的 torch/_inductor/fx_passes/micro_pipeline_tp.py 会对编译图运行一个 pass：

# micro_pipeline_tp.py:1087
def micro_pipeline_tp_pass(graph: torch.fx.Graph):
    all_gathers    = find_all_gather_patterns(graph)      # 找 all_gather → matmul 消费者
    reduce_scatters = find_reduce_scatter_patterns(graph) # 找 matmul → reduce_scatter 生产者
    ...
    for all_gather in all_gathers:
        fuse_all_gather_matmul(all_gather)         # :614
    for reduce_scatter in reduce_scatters:
        fuse_matmul_reduce_scatter(reduce_scatter) # :862

find_all_gather_patterns 匹配编译图里的 _c10d_functional.all_gather_into_tensor → wait_tensor（0 维 gather），以及 all_gather → split → cat（非 0 维 gather，DTensor 的常见表达）； 然后只挑出下游是 matmul（或 reshape→mm→reshape、scaled_mm）的模式。

pass 不是无脑替换，只有满足条件才融合，否则保持原样（正确性不变）：

  • 对应通信组必须已启用 symmetric memory（is_symm_mem_enabled_for_group）；
  • all-gather 结果必须确实被 matmul 消费；若还有其他用户，则需要保留完整 A；
  • matmul 类型必须一致（普通 mm 或 scaled mm），matmul 的其他输入不能依赖 all-gather 结果；
  • gather/scatter 是最后维时要求分片维 ≥1024，且 scaled_mm 暂不支持最后维融合；
  • matmul → reduce-scatter 融合要求 matmul 结果只有 reduce-scatter 一个用户。

5. 对称内存与融合算子内部

Inductor 替换出的目标是 torch.ops.symm_mem.* 自定义算子，实现在 torch/distributed/_symmetric_memory/__init__.py。主要算子：

算子改写前语义内部做了什么
symm_mem.fused_all_gather_matmul
（含 scaled_mm 变体）		 A = all_gather(A_shard); C_i = A @ B_i 按 gather dim 切块，每收到一块 A_i 就执行对应 matmul；可同时服务多个 B
symm_mem.fused_matmul_reduce_scatter
（含 scaled_mm 变体）		 Y = A @ B; rs = reduce_scatter(Y) 边算边把给每个 rank 的结果分片发出去，通信与 matmul 尾部重叠

内部实现有两类关键布局：

  • gather_dim 不是最后维（最常见：all-gather 沿序列维，再 @ B）： A_full 按源 rank 切成 A_0…A_{P-1}，每个输出块 A_i @ B 独立。 实现里把 A_shard 的 gather dim 移到最前并展平成 2D，为每个输出块分配 output_shards[rank]，然后调用 _pipelined_all_gather_and_consume。
  • gather_dim 是最后维：A_full 是“列拼接”，结果需要把各分片的部分和累加。 实现把 B 按 rank 切成 B_shards，每收一块就 mm.out / addmm_ 累加进输出， 用 CUDA event 保证累加顺序正确。

这里的“通信”不是完整等一整次 NCCL all-gather 再继续，而是通过 symmetric memory 的 peer p2p buffer + barrier 让每个 rank 按块读远端分片：数据一到就执行 shard_consumer（matmul）。代码里用 symm_mem.barrier(channel=…) 在“写 buffer / 读 buffer / 覆盖 buffer”之间同步，用两条流交替放 copy 和 matmul，让它们可以同时占用 GPU。 reduce-scatter 方向则反向用 _pipelined_produce_and_all2all：本地先算好要发给各 rank 的分片， 写进自己的 p2p buffer，远端边拷边累加。

与 NCCL 的关系 Async TP 不是给 NCCL 增加一种“非阻塞 all-gather 算法”。当融合条件满足时，它绕过整块 collective， 改为 symmetric memory 的 p2p 拷贝 + 双流调度；只有未融合的 fallback 或非 symm-mem 路径才回到普通 _c10d_functional → NCCL。CUDA 侧真正干活的仍是拷贝 kernel、matmul kernel 和 barrier/event。

6. 效果、要求与限制

仓库自带 benchmarks/asyncTP_llama3_h100_2025-06_torchtitan.md 的实测（H100，NVLink）： Async TP 在 bf16 下约 +9~10%，在 FP8 tensor-wise 量化下可达约 +16%。

前提条件
  • 必须启用 torch.compile 且编译 model 组件；
  • TP 通信组需要可用 symmetric memory（NVLink 或类似直连拓扑）；
  • 只有被 Inductor 成功匹配的模式才会融合；其它 all-gather / matmul 保持普通路径；
  • 该实现依赖 PyTorch 内部（_micro_pipeline_tp、symm_mem），随版本演进可能变化；
  • 切块 matmul / 累加顺序可能与原实现略有不同，结果应在数值容差内一致，但不能承诺逐 bit 相同。

7. 对照与 FAQ

问题答案
TorchTitan 为 Async TP 写了多少代码？ 只有 ParallelismConfig 开关（configs.py:137）+ maybe_enable_async_tp （tensor_parallel.py:102）把 torch._inductor.config._micro_pipeline_tp 置 True。核心实现全在 PyTorch。
Async TP 是新的 NCCL 通信算法吗？ 不是。它是 Inductor 图形级“all-gather + matmul”融合；算子内部用 symmetric memory 的 p2p 拷贝与双流把通信按块和计算重叠。
和 redistribute(async_op=True) 有什么区别？ async_op 只是让 collective 异步启动、后置 wait；Async TP 更进一步：通信本身按小块暴露给 matmul，做通信-计算微流水线。
哪些模型可用？ llama3、qwen3、qwen3_5、deepseek_v3、kimi_k2_7、muse_glimmer 等 parallelize 入口都调用 maybe_enable_async_tp；开关是否有效取决于具体编译图是否命中融合模式。
为什么要 symmetric memory？ 因为要在融合算子内部“收到一块就算一块”。普通 NCCL collective 对外只暴露完整结果；symmetric memory 让 GPU 能直接读写 peer 的共享缓冲区， 配合 barrier 才能安全地边收边算。
开启后数值会完全一致吗？ 数学语义等价；但 all-gather 沿最后维、reduce-scatter 等场景会改变部分和的顺序，浮点结果可能略有差异。torchtitan 把它当作需要独立收敛验证的优化路径。
一句话总结 Async TP = “把 TP 边界的一次整块 all-gather/reduce-scatter，拆成通信与 matmul 交替的微流水线”。 TorchTitan 只负责开 _micro_pipeline_tp；Inductor 在编译图里把 all_gather→matmul / matmul→reduce_scatter 换成 symm_mem 融合算子； 算子再用对称内存 + 双 CUDA 流让通信和计算真正重叠。

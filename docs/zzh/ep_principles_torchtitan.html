1. 为什么需要 EP：MoE 的问题与 EP 的答案

MoE（Mixture of Experts）把 Transformer 每层的 FFN 换成“一个 Router + 很多个专家 FFN”。每个 token 只激活其中 top_k 个专家，因此 计算量不随专家数线性增长；但 参数量随专家数线性增长，训练时必须解决“这么多专家权重放哪里”的问题。

torchtitan 本仓库里自带的 DeepSeek V3 系配置正好能说明数量级（models/deepseek_v3/__init__.py）：

flavordim层数路由专家数 Etop_k共享专家配置入口
debugmodel2566832deepseek_v3_debugmodel
16B2048276462deepseek_v3_16b（EP=8）
236B51206016062模型入口 model_registry("236B")
671B71686125681deepseek_v3_671b（EP=2）

以 236B 的数值粗算：单个专家三层 FFN 权重约 3 × 1536 × 5120 ≈ 23.6M； 160 个路由专家一层约 3.77B，59 层 MoE 合计约 222B。若 EP 把 160 个专家切成 4 份， 每张卡只持有 40 个专家的权重，单层路由专家权重降到约 0.94B。

EP 的本质 DP/FSDP/TP/CP/PP 是“把同样的计算拆给不同卡、数据不搬家”；EP 相反——token 会被路由到任意一张卡上的专家，所以必须“数据跟着计算走”，用 all-to-all 把 token 先送到持有目标专家的卡，算完再送回来。

2. Router：先决定 token 去哪些专家

torchtitan 的默认路由是 token-choice top-k，实现在 torchtitan/models/common/moe.py:193 的 TokenChoiceTopKRouter。前向逻辑（moe.py:285）：

def forward(self, x_BLD, expert_bias_E=None):
    # gate 只是 D→E 的线性层；在 float32 下计算保证稳定
    scores_BLE = autocast_float32(self.gate(x_BLD))       # (B, L, E) 每个 token 对每个专家的分数
    if self.score_func == "sigmoid":  scores_BLE = sigmoid(scores_BLE)
    elif self.score_func == "softmax": scores_BLE = softmax(scores_BLE, dim=-1)

    scores_for_choice_BLE = scores_BLE + expert_bias_E   # 选路时可加 bias，但不改输出分数
    # 可选：先按专家分组过滤（node-limited），减少跨节点通信
    topk_expert_ids_BLK = topk(scores_for_choice_BLE, k=top_k)   # 每个 token 选 K 个专家
    topk_scores_BLK = scores_BLE.gather(dim=-1, index=topk_ids) # 分数仍取自原始 sigmoid/softmax
    if self.route_norm: topk_scores_BLK /= sum(topk_scores_BLK)
    topk_scores_BLK *= self.route_scale
    return topk_scores_BLK, topk_expert_ids_BLK, scores_BLE

DeepSeek V3 家族在这里还带两个可选开关：

  • node-limited / group-limited routing（num_expert_groups、num_limited_groups）： 先把 E 个专家分成若干组，只允许 token 从得分最高的 num_limited_groups 组里选 top-k， 减少一次 all-to-all 里跨节点的比例。
  • expert_bias_E：由 MoE.expert_bias_E buffer 提供，参与“选择”但不进入输出分数， 用于后续讲的 aux-loss-free 负载均衡。

3. All-to-all：把 token 送到专家所在的卡

EP 与“每次激活全部专家”的并行不同：每个 token 的 top-k 是 数据相关的，因此每个 rank 发给其他 rank 的 token 数不固定。PyTorch 的 all_to_all_single 支持不等长切分， 但调用前必须知道每个接收方要收多少行。所以标准 EP dispatcher 实际做 两次 all-to-all：

第 1 次：交换“每个专家的 token 数” 本地 token 只知道自己把 token 分给谁。把 num_local_tokens_per_expert_E 按 (EP, E/EP) 切， 用一次小 all-to-all 让每个 rank 知道“其他 rank 将发给我的每个本地专家多少 token”。

第 2 次：交换 token 数据本身 用第 1 次得到的分割长度（input_splits / output_splits）做数据 all-to-all， 把 token 行发给持有目标专家的 rank。GPU 上无法动态拼接变长通信，需要把 split 长度取回 CPU， 这是 EP 中一次不可避免的 device-to-host 同步。 
# token_dispatcher.py: AllToAllTokenDispatcher
def _token_count_exchange(self, num_local_tokens_per_expert_E, pg, ep_size):
    return all_to_all_single(
        num_local_tokens_per_expert_E.view(ep_size, -1),  # (EP, E/EP)
        None, None, group=self.ep_mesh)

def dispatch(self, x_TD, topk_scores_TK, topk_expert_ids_TK, num_local_tokens_per_expert_E):
    routed_input_ND, token_indices, scores = self._local_reorder(...)  # 先把本地 token 按专家号排序
    # ① count all-to-all —— 得到每个本地专家一共要收多少 token
    num_global_tokens_per_local_expert_EP_e = self._token_count_exchange(...)
    input_splits, output_splits = self._sync_token_count_exchange(...)  # 切分长度取回 CPU
    # ② data all-to-all —— 真正把 token 送到持专家权的 rank
    routed_input_RD = self._dispatch_token_exchange(routed_input_ND, pg, output_splits, input_splits)
    # ③ 收到的行目前是 “按发送方排序”，再重排成 “按本地专家排序”
    input_shape, routed_input_RD, permuted_indices, per_local_expert = self._permute(...)
    return routed_input_RD, per_local_expert, metadata

def combine(self, routed_output_RD, metadata, x_TD):
    routed_output_RD = self._unpermute(routed_output_RD, ...)  # 还原 rank-major
    routed_output_RD = self._combine_token_exchange(...)       # 反向 all-to-all，结果送回原 token 的 rank
    out_TD = routed_output_RD.to(float32) * topk_scores_experts_sorted_N
    return deterministic_scatter_add(out_TD, token_indices, routed_output_RD)

3.1 两次重排：rank-major → expert-major → rank-major

数据 all-to-all 完成后，每个 EP rank 收到的是“按发送方 rank 排”的行： (src0 的本地专家 0), (src0 的本地专家 1), …, (src1 的本地专家 0), …。 而 grouped GEMM 希望“按本地专家排”：每个专家收到来自所有 src 的 token 连成一段。 所以 _permute（token_dispatcher.py:474）做一个矩阵转置式的索引重排；combine 时用记录的 permuted_indices 原路还原。

3.2 专家计算与 combine

专家本体是 GroupedExperts（moe.py:35）。三个参数直接以 (E, *, *) 的“打包”3D 形状存放：w1_EFD (E,F,D)、w2_EDF (E,D,F)、 w3_EFD (E,F,D)。EP 下 E 是本地专家数。前向用 torch._grouped_mm 一次对“每组 token”做独立矩阵乘：

# 简化：省略 bf16 转换与 DTensor.to_local()；EP 下 x_RD 已是本地 token 行
def forward(self, x_RD, num_tokens_per_expert_E):
    offsets_E = cumsum(num_tokens_per_expert_E, dim=0)   # 每个专家组的行偏移
    h_RF = silu(self._grouped_mm(A=x_RD, B_t=w1_EFD, offs=offsets_E))
    h_RF = h_RF * self._grouped_mm(A=x_RD, B_t=w3_EFD, offs=offsets_E)
    return self._grouped_mm(A=h_RF, B_t=w2_EDF, offs=offsets_E)

combine 是 dispatch 的镜像：先 unpermute，再 all-to-all 把结果送回原始 rank，乘以 top-k 路由分数， 再用 deterministic_scatter_add 把同一个 token 的 K 份专家输出累加回该 token 的行。 乘法在 float32 做，保证小分数下数值稳定。

5. 双 Mesh 与专家权重切分

5.1 一个世界，两张 mesh

torchtitan 的并行维度名定义在 distributed/parallel_dims.py:31： dp_replicate / dp_shard / fsdp / tp / cp / pp / ep / efsdp。 关键点：EP 不是把 GPU 数量再乘一个 EP 度，而是把同一批 GPU 重新分组。

# parallel_dims.py:203-274（简化）
fsdp   = dp_shard * cp
efsdp  = fsdp * tp // ep            # “专家区的 FSDP 轴”

# 稠密区（attention / 共享专家 / 其它 dense 参数）
dense_storage_mesh_axes  = [pp, dp_replicate, dp_shard, cp, tp]
# 专家区（routed experts 权重）
sparse_storage_mesh_axes = [pp, dp_replicate, efsdp, ep]

# 两边都能还原世界大小：
# dense :  pp × dp_replicate × dp_shard × cp × tp = world
# sparse:  pp × dp_replicate × efsdp × ep      = world（因为 efsdp = dp_shard·cp·tp / ep）

也就是说，专家参数被放进一张与 dense 参数“正交的另一种因式分解”的 mesh 上： ep 轴决定“哪些专家在本地”，efsdp 轴继续承担 FSDP 的“参数再分片 / all-gather”。 这也解释了 full_dtensor.py:56-57 里的两组常量：

_DENSE_STORAGE_AXES  = ["dp_replicate", "dp_shard", "cp", "tp"]
_SPARSE_STORAGE_AXES = ["dp_replicate", "efsdp", "ep"]

5.2 专家权重在 EP 轴上的声明

EP 的核心声明只有几行（moe_sharding.py:29）：

def expert_param_placement_sparse() -> SpmdLayout:
    return SpmdLayout({
        DP_REPLICATE: spmd.R,        # HSDP 复制轴（存储期 Replicate，FSDP 处理）
        EFSDP:        spmd.R,        # FSDP 存储轴（分片交给 fully_shard）
        EP:           spmd.S(0),     # ← EP 永远沿 dim 0：专家维
    })

w1_EFD / w2_EDF / w3_EFD 的第一个维度是专家维，因此 EP 对它们统一用 Shard(0)； 而 expert_param_placement_dense（EP=1、TP>1 时）才需要区分 colwise 的 Shard(1) / rowwise 的 Shard(2)——那是“不切专家、只做普通 TP”的另一条路。

阶段w1_EFD（示意 E=160, F=1536, D=5120）说明
逻辑形状(160, 1536, 5120)打包成 3D 参数的 160 组 FFN
EP=4 之后每 rank (40, 1536, 5120)40 = 160 / 4，沿 ep 轴 Shard(0)
再叠 efsdp FSDP每 rank ≈ (40/(efsdp) 或 F 切分, …)由 apply_fsdp_to_decoder 的 Shard(0)/Shard(1) 策略决定；专家充足时仍切专家维
FSDP 里的 expert 特判 fsdp.py:110 的 apply_fsdp_to_decoder 遍历 MoE transformer block：普通参数留在 dense dp_mesh， 路由专家参数通过 shard_placement_fn 路由到 edp_mesh（dp_replicate, efsdp, ep）。 EP 开启后还会显式设置跨层的 FSDP prefetch，因为 EP 的 host sync 会干扰 FSDP 默认隐式预取。

6. Dispatcher 家族：五种 token 分发实现

torchtitan 把“token 重排 + 通信”从模型里抽成了 TokenDispatcher， 通过 comm_backend 配置选择实现（config_utils.py:311）。所有实现都遵循同一个接口： dispatch() 返回“本地专家按 expert-major 排好的 token” + 元数据，combine() 负责送回去。

6.1 DeepEP 的异步 combine 与 HybridEP 的非阻塞 dispatch

MoE.forward（moe.py:409）里的顺序是：先跑 routed experts，再跑 shared experts， 最后相加。标准 all-to-all 的 combine 是同步的，通信时间直接暴露；DeepEP v2 的 combine 则返回后不立刻等， 让 shared_experts 的计算与 combine 通信重叠，等真正要用结果前再 sync_combine()（moe.py:477-479）。 HybridEP 则把重心放在 GB200/NVLink72 上的 dispatch：用 TMA + 预设容量做 CPU-free 非阻塞分发；它的 combine 仍按同步路径执行。

7. 训练配套：负载均衡、FSDP 与 checkpoint

7.1 aux-loss-free 负载均衡（expert bias）

EP 的通信量取决于各 rank 收到的 token 数是否均匀。DeepSeek V3 用“无辅助损失的负载均衡” （arXiv:2408.15664），torchtitan 的实现放在 components/optimizer.py:386：

  1. 每个 MoE 层维护 tokens_per_expert_E buffer；MoE.forward 在 no_grad 下累计每个专家本步收到的 token 数。
  2. 每个 optimizer step 前，先把所有层、所有并行 rank 的计数规约成全局计数（loss mesh / DTensor redistribute）。
  3. 对每个专家更新 bias：
# optimizer.py:514-520（代码注释也承认：与论文并不完全一致）
expert_bias_delta_E = load_balance_coeff * torch.sign(
    tokens_per_expert_E.mean() - tokens_per_expert_E)
expert_bias_delta_E = expert_bias_delta_E - expert_bias_delta_E.mean()
moe.expert_bias_E.add_(expert_bias_delta_E)
moe.tokens_per_expert_E.zero_()

偏置只影响 topk 的选择，不影响输出分数（见 Router 一节），因此不会破坏训练目标； 它会让“用得少的专家”在下次路由时更容易被选到。若激活重计算开启，代码按“计数被算了两遍”处理，除以 2 修正。

7.2 EP 与 FSDP / checkpoint 的耦合

  • FSDP 分 mesh：非专家参数在 dense mesh 上 FSDP，路由专家参数由 shard_placement_fn 放到 sparse mesh 上， 所以一块 MoE transformer block 内部可以同时属于两套 FSDP 单位。
  • 显式 prefetch：EP >1 时 apply_fsdp_to_decoder 手动设置相邻层 forward/backward 的 FSDP prefetch， 避免 count exchange 的 host sync 打断 FSDP 的隐式预取（fsdp.py:332+）。
  • checkpoint adapter：HF 存的是“每个专家一个 2D 权重”，torchtitan 存的是打包 3D 权重； MoEStateDictAdapter（models/utils.py）需要把 3D 拆回 2D 逐专家读写，并能处理 [StridedShard(0), Shard(0)] 这种 EP+FSDP 同切专家维的布局。

8.1 用户层做什么？

  • 选模型与并行度：MODULE=deepseek_v3 CONFIG=deepseek_v3_671b； 对 671B 来说 EP 必须开启，用户决定 expert_parallel_degree（仓库默认 2，也可 CLI 设 4/8）。
  • 选 MoE 通信后端：默认 moe_comm_backend="standard"；在 GB200 上可切 hybridep，或装 DeepEP 后切 deepep（由 model_registry 参数传入）。
  • （扩展新模型时）声明结构：用户模型代码只需给出 MoE.Config / RoutedExperts.Config / TokenChoiceTopKRouter.Config， 例如 256 个专家、top_k=8、共享专家数、router 的 sigmoid / 组限制；torchtitan 的 sharding 系统负责把它解释成并行布局。
  • 不做的事：用户不写 all-to-all、不写 NCCL 调用、不手动搬权重；EP 是“配置出来的”，不是“手写出来的”。

8.2 TorchTitan 层做什么？

  • 建 mesh：ParallelDims 根据 world_size 和 ep 度建 dense mesh 与 sparse mesh； 671B EP=4 时每个 rank 在 ep 轴上只对 64 个专家负责。
  • 写布局声明：set_deepseek_v3_sharding_config → set_moe_sharding_config 把 “哪些参数切、切哪个轴、激活什么布局、路由计数 Partial”填进每个 Module 的 sharding_config。
  • 接 FSDP：apply_fsdp_to_decoder 用 shard_placement_fn 把专家参数放上 sparse/edp mesh， 其余参数留在 dense mesh；EP 下还会显式排相邻层的 FSDP prefetch。
  • 跑前向编排：MoE.forward 负责“router 出分数 → 数每个专家的 token → 交给 token dispatcher → GroupedExperts → combine → 与 shared expert 相加”，并处理序列 padding、DeepEP 的 sync_combine 等边界。
  • 训练配套：统计 tokens_per_expert_E，在 optimizer step 前更新 expert_bias_E， 做 aux-loss-free 负载均衡；checkpoint 层负责把打包的 3D 专家权重和 HF 的逐专家 2D 权重互转。

8.3 PyTorch 层做什么？

  • 进程组与 DeviceMesh：init_device_mesh 为 ep 轴创建真实通信组； AllToAllTokenDispatcher 拿到的 ep_mesh 就是从这里来的。
  • DTensor / placement：用 Shard(0) 表达“专家维被 EP 切开”，用 Partial/Replicate 表达路由计数与共享专家； FSDP2 负责在 efsdp 轴上再分片。
  • 集合通信原语：标准后端调用 all_to_all_single（functional collective）， 传入 ep 进程组与切分长度；count 和 data 两次 all-to-all 都由它发起。
  • 计算算子：torch._grouped_mm 把 64 组本地专家的 GEMM 一次调度； topk / argsort / scatter_add 等算子用于路由与 combine；这些本身由 CUDA kernel 实现。
  • 可扩展算子边界：DeepEP/HybridEP 通过 torch.library 自定义算子进入同一套 autograd / torch.compile 图， dispatcher 接口让切换后端不影响 MoE 模型代码。

8.4 CUDA & NCCL 层做什么？

  • 执行 all-to-all：NCCL 在 EP 通信组上搬运 token 数据。它不认识“专家”： 只按 PyTorch 给出的 split 长度，把每个 rank 缓冲区里的行送到对应 rank。
  • 执行 grouped GEMM：671B 每层 MoE 有 64（EP=4）个本地专家，每个专家是一个 2048×7168 / 7168×2048 的 FFN；GPU 端用 grouped GEMM kernel 一次性按专家分段计算， 比 64 次独立 GEMM 启动更高效。
  • 跑路由周边 kernel：top-k、按专家 argsort、token 计数、permute 索引、scatter_add 等都在 GPU kernel 内完成； 唯一需要 CPU 介入的是把变长 all-to-all 的 split 长度从 device 拷回 host。
  • 硬件拓扑相关优化：DeepEP/HybridEP 针对 NVLink、NVLink72/GB200 使用 TMA、多 SM、独立通信流； combine 通信可与 shared experts 计算重叠，最终靠 CUDA event 同步。

8.5 把 671B 的一次 MoE forward 过一遍

具体数字示例（EP=4、每 rank 64 个本地专家） 假设每个 rank 本地有 T=16,384 个 token（例如 batch 4 × seq 4096），top_k=8 → N=131,072 条“token-专家”记录。 路由后约 1/4 的 token 命中本地专家，其余 3/4 需要 all-to-all 送去其他 3 个 rank；均衡时每 rank 净收 ~N/4=32,768 行。 每层 MoE 重复一次 count all-to-all + data all-to-all + combine all-to-all。

这四层各自的“一秒钟” 用户写配置 → TorchTitan 算出 mesh 与布局 → PyTorch 发 all-to-all / 调度 grouped GEMM → NCCL 在 NVLink 上搬 32,768 行、 GPU kernel 算 64 个本地专家的 FFN；反向传播时同一流程倒着再来一遍，并由 autograd 自动把 dispatch/combine 的梯度接回 router。

9. 快速对照与 FAQ

问题答案
EP 和 TP 都切专家权重吗？ EP=1 且 TP>1 时，torchtitan 走 expert_param_placement_dense：把单个专家的 F/D 维像普通 FFN 一样 colwise/rowwise 切。 EP>1 时走 expert_param_placement_sparse：优先沿 专家维（dim 0）切。两者不是同一件事。
EP 度有什么约束？ ep 必须能整除 num_experts（dispatcher 会校验）；同时 efsdp = dp_shard × cp × tp / ep 必须仍是整数， 否则 mesh 建不出来。EP 不在 ParallelDims._validate 的乘法里，而是通过 sparse mesh 与 dense mesh 共用 GPU 来满足 world_size。
一次 forward 到底跨卡通信几次？ 标准 AllToAll 每层 MoE：1 次 count all-to-all + 1 次 dispatch all-to-all + 1 次 combine all-to-all。 DeepEP/HybridEP 把 combine 异步化；MinimalAsyncEP 用对称内存把 count 阶段合并进一次异步 dispatch。
共享专家（shared expert）走 EP 吗？ 本仓库 DeepSeek V3 的 shared_experts 是普通 FeedForward，按 dense 族布局处理（可再叠 FSDP/TP）， 不参与 routed experts 的 all-to-all。它每层每个 token 都算，所以放在 dense mesh 更合理。
为什么 route 之前要把 token 本地排序？ all-to-all 的切分按“连续区间”发送。token 先按目标专家号排好，才能把“发给同一 rank 的 token”聚成一个连续分片；收到的 rank 也才能按专家块处理。
负载不均衡会怎样？ 某几个专家收到的 token 特别多时，对应 rank 的 grouped GEMM 成为瓶颈，其他 rank 空等； all-to-all 的 split 也会更不均衡。训练期用 expert bias 做无辅助损失均衡；调试时可用 --debug.moe_force_load_balance 强制轮转路由验证数值。
最小化例子怎么跑？ MODULE=deepseek_v3 CONFIG=deepseek_v3_debugmodel ./run_train.sh；16B EP=8 见 config_registry.py:165；671B EP=2 见 :234。实际大规模部署常把 ep 设成 4/8 并用 CLI 覆盖。
一句话总结 MoE 让“参数量随专家数增长、计算量不随专家数增长”；EP 再把专家权重按 ep 轴切开， 用两次（或一次异步）all-to-all 让 token 跟着路由走：先数 token、再送 token、按专家算、送回 scatter_add。 torchtitan 的工程化要点是：声明式 sharding（EP 切 dim 0）、sparse mesh 与 dense mesh 复用同一批 GPU、 dispatcher 可插拔（standard / torchao / DeepEP / HybridEP / MinimalAsyncEP）。

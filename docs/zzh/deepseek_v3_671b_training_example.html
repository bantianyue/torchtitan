0先回答你的核心问题

问:torchtitan/models/deepseek_v3/ 下的文件,也应该是用户开发的吧?

答:对,但要分两个身份看。
  1. 作为"现成支持模型"--它已经在仓库里、在 models/__init__.py 的 _supported_models 名单里(["deepseek_v3","flux","gpt_oss","llama3","qwen3","qwen3_5"]),走完整 CI。你要训练 DeepSeek V3 671B,这个目录你一行都不用改,直接 --module deepseek_v3 --config deepseek_v3_671b 就能用。
  2. 作为"添加新模型的模板"--docs/extension.md 和 models/README.md 白纸黑字写着:"要注册一个模型,在 __init__.py 里定义 model_registry(flavor) 返回 ModelSpec,在 config_registry.py 里定义训练配置,参考 torchtitan/models/llama3。" 这套七文件结构,正是你为"任何新模型"要照着写的"用户代码"。
所以 deepseek_v3/ 同时是"官方维护的成品"和"你开发新模型时的范本"。两者不矛盾:它就是 torchtitan 团队按"用户扩展点"规范自己先实现的一个范例。

图 0-1:deepseek_v3/ 既是"拿来即用"的官方模型,也是"你写新模型"的范本。两条路径同一个目录。

一句话记住:"用户开发"的不是 deepseek_v3 这个目录本身(它已存在),而是这套七文件结构所体现的扩展点契约。训练 671B 时你开发的是配置/命令;训练新模型时你开发的是同样结构的目录。下面分开讲。

1三层代码归属:谁开发什么

把"训练一个模型"这件事的代码,按归属分成三栏。这是本页最重要的图--它决定了你该碰哪些文件、不该碰哪些。

图 1-1:三层归属。① torchtitan 核心(框架,不改) -> ② 模型扩展目录(扩展点契约,deepseek_v3/ 是范例) -> ③ 运行时配置(你每次写)。箭头方向 = 依赖方向:② 只调①,③ 只选/覆盖②。

核心原则(来自 CLAUDE.md):"Don't leak experiments into core"--别为实验需求改 ①。① 的并行/组件是模型无关的;模型相关的东西(架构、哪个权重切哪维、HF 键名)放 ②;一次性配置放 ③。

2deepseek_v3/ 七个文件各调哪些 torchtitan API

这是本页的"干货"。逐文件列出它从 torchtitan import 了什么、调了什么,你就能看出:所谓"用户开发"其实大量是调用框架 API,真正模型相关的只有架构本身和切分声明。

文件职责从 torchtitan 调用的 API性质
model.py 单卡架构:MLA attention + MoE block + 模型类 继承 Decoder/TransformerBlock/Module(protocols/module);用 models/common/ 的 BaseAttention,FlexAttention,Linear,RMSNorm,RoPE;get_moe_model_nparams_and_flops(models/utils);get_spmd_backend(distributed/utils);spmd_types 的 spmd.local()/spmd.assert_type。在 Config.update_from_config() 里调本目录 set_deepseek_v3_sharding_config()。 模型相关
sharding.py 声明每个权重怎么放(colwise/rowwise/replicate) ShardingConfig(protocols/sharding);共享 helper colwise_config/rowwise_config/norm_config/dense_param_placement/set_decoder_sharding_config/set_dense_ffn_sharding/set_gqa_inner_attention_local_map(models/common/decoder_sharding);set_moe_sharding_config(models/common/moe_sharding)。 模型相关
parallelize.py 切分编排:决定先 CP 还是先 parallelize、何时 FSDP/compile 全是顺序调用:validate_config/model.parallelize(parallel_dims);CP apply_cp_to_forward(distributed/context_parallel);TP maybe_enable_async_tp(distributed/tensor_parallel);AC ac_config.build().apply(model);compile apply_compile(distributed/compile);mesh resolve_fsdp_mesh/resolve_sparse_fsdp_mesh 或 parallel_dims.get_mesh();FSDP apply_fsdp_to_decoder(distributed/fsdp)。 编排 纯调①
__init__.py model_registry(flavor) 组装 ModelSpec + 定义各尺寸架构数 返回 ModelSpec(protocols/model_spec)字段:name/flavor/model/parallelize_fn=parallelize_deepseekv3/pipelining_fn=pipeline_llm(torchtitan 通用,非本目录写)/post_optimizer_build_fn=register_moe_load_balancing_hook/state_dict_adapter=DeepSeekV3StateDictAdapter。用 Float8LinearConverter/Float8GroupedExpertsConverter(components/quantization)。 组装 借①组件
config_registry.py deepseek_v3_671b() 等返回 Trainer.Config 用 Trainer.Config(trainer);组件 default_adamw/CrossEntropyLoss/ChunkedLossWrapper/LRSchedulersContainer/MetricsProcessor/CheckpointManager.Config(components);SelectiveAC(distributed/activation_checkpoint);HuggingFaceTextDataLoader(hf_datasets);TrainingConfig/ParallelismConfig/CompileConfig(config);decoder_vocab_size(models/common/config_utils)。 纯配置
state_dict_adapter.py torchtitan 权重名 <-> HF 权重名映射 继承 MoEStateDictAdapter(models/utils)->BaseStateDictAdapter(protocols/state_dict_adapter);用 DTensor(torch.distributed.tensor)、HuggingFaceStorageReader。仅一张 from_hf_map 字典。 模型相关 可选
README.md tokenizer/权重下载说明 无 API 调用,纯文档。 文档
读表得出的结论:
  • 真正"模型相关"的只有三件:model.py(架构,但用 common 组件搭)、sharding.py(哪个权重 colwise/rowwise,但用共享 helper)、state_dict_adapter.py(HF 键名表)。其余都是组装和顺序调用。
  • parallelize.py 一行业务逻辑都没有--它就是"CP -> parallelize -> async_tp -> AC -> compile -> FSDP"的调用顺序,这些 apply_* 全在 ①。
  • PP 不是本目录写的:pipelining_fn=pipeline_llm 来自 torchtitan/distributed/pipeline_parallel.py,是模型无关的通用函数。换任何模型都用它。
  • config_registry.py 是纯数据:一组数字(lr/batch/seq/steps/并行度),没有任何逻辑,完全可被 CLI 覆盖。

图 2-1:parallelize_deepseekv3 的调用顺序(源码 parallelize.py 逐行核对)。注意 PP(第 7 步)不在本函数里--它由 ① 的 pipeline_llm 驱动,对每个 stage 调本函数一次。

5"你写 vs 框架给"总表

把全篇收成一张表:训练 DeepSeek V3 671B,每一件事归谁。

最终结论:
  • 训练现成的 671B:你只做 ③--写命令(选 module/config、给并行度、配多节点、备 tokenizer/数据)。deepseek_v3/ 目录(②)和 torchtitan 核心(①)都不用碰。
  • 训练一个新模型:你做 ② + ③--照 deepseek_v3/ 的七文件结构写自己的目录(其中 parallelize.py/config_registry.py 大量是调①的 API,真正要写的只有架构和切分声明),再加 ③ 的命令。
  • ② 永远只调①,不实现①--所以"用户开发"的本质是"按 ModelSpec 七字段契约组装 + 调用框架的 apply_* / 共享组件",而非从零造分布式训练轮子。

6ModelSpec 生命周期:② 如何被 ① 消费

前面讲清了"② 的七字段 ModelSpec"和"① 提供的 API"。这一节把二者接起来:训练启动时,Trainer 到底怎么一步步把 ② 的 ModelSpec 变成可训练的并行模型。这条链路里你写的部分(②)只是被调用的几个回调和一张 Config,主流程全是 ① 在驱动。

图 6-1:ModelSpec 生命周期。左列是 ① Trainer 驱动的主流程(trainer.py:220-520),右列是 ② ModelSpec 七字段被消费的 4 个点。绿色=PP 分支,蓝=通用步骤,紫框=② 的回调点。最右列 ③ 只在 step1 提供输入。

时序图看出的真相:
  • 主流程是 ① 在驱动:10 步里 8 步是 ① 的 Trainer.__init__ 在自己跑(config 解析、建 mesh、建 optimizer、初始化权重、进 train loop)。
  • ② 被回调只有 4 处:step3 model 喂给 build、step4 pipelining_fn+parallelize_fn 做切分、step8 post_optimizer_build_fn 挂 MoE hook、step9 state_dict_adapter 建 HF 互转。这正好对应 ModelSpec 的七个字段。
  • ② 的 parallelize_fn 自己又被拆成 6 个 apply_*(图 2-1),所以"用户开发"到最底层仍是调 ①。
  • PP 分支与非 PP 分支的区别:PP 多走 pipeline_llm 切 stage + 建 schedule,且对每个 stage 各调一次 parallelize_fn;非 PP 直接调一次 parallelize_fn。671B 用 Interleaved1F1B,走 PP 分支。
  • ③ 只在最开头露面:提供 --module/--config/--parallelism.* 与 tokenizer/数据,之后整个训练都不再需要你介入。

7用户真正要写的代码/配置(可直接复制)

前面全是"谁写什么"的说明。这一节把用户实际落笔写的东西原样给出来,按"从简到繁"三档:① 一行命令跑现成的 671B;② 自定义一个训练配置(不改 core);③ 不改源码换组件(override)。所有代码对照源码核验,改个路径即可用。

7.1 第一档:直接跑现成的 671B(你只写命令)

现成的 deepseek_v3_671b 配置已在仓库里,你一行 Python 都不写,只准备命令和外部资源。

7.2 第二档:自定义一个 671B 训练配置(不改 core)

现成的 deepseek_v3_671b 是 lr=2.2e-4 / warmup=2000 / EP=2 / Interleaved1F1B。若你要改 lr、warmup、并行度组合、checkpoint 频率等,有两种做法:(A) 直接 CLI 覆盖单次值(最轻);(B) 写一个自己的 config_registry 函数固化下来(团队复用)。下面给 B 的完整文件。

7.2a 最轻:CLI 直接覆盖(不写任何文件)

# 只覆盖你想改的字段,其余继承 deepseek_v3_671b 的默认值
torchrun --nproc_per_node 8 -m torchtitan.train \
    --module deepseek_v3 --config deepseek_v3_671b \
    --parallelism.tensor_parallel_degree=4 \
    --parallelism.pipeline_parallel_degree=8 \
    --parallelism.expert_parallel_degree=4 \
    --parallelism.data_parallel_shard_degree=-1 \

7.3b 写自己的 override 模块(替换任意 Configurable,以换 optimizer 为例)

对照源码核验的 override 写法(overrides/fused_swiglu.py:483 的 @override + derive):@override(name, target=被替换的Config, description=) 装饰一个工厂函数,返回新 Config。下面给一个最小的"换 optimizer"骨架。

# 文件:torchtitan/experiments/my_dsv3/overrides.py
from torchtitan.components.optimizer import OptimizersContainer
from torchtitan.config import override

# 假设你写了个带 weight decay 调优的 AdamW 容器
class MyAdamW(OptimizersContainer):
    class Config(OptimizersContainer.Config):
        weight_decay: float = 0.1

@override(
    "my_adamw",                          # 名字,用于 --override.apply
    target=OptimizersContainer.Config,      # 被替换的目标 Config
    description="AdamW with tuned weight decay",
)
def my_adamw(cfg: OptimizersContainer.Config) -> MyAdamW.Config:
    from torchtitan.config import derive
    return derive(cfg, MyAdamW.Config, weight_decay=0.1)

# 用:
#   --override.imports torchtitan.experiments.my_dsv3.overrides
#   --override.apply optimizer=my_adamw      (按 FQN glob 精确指定时再细化)
override vs config_registry 的区别:config_registry 是建一个新配置(改超参/并行度);override 是把某个组件类换掉(换 optimizer/loss/attention 实现),不动 config 逻辑。两者可叠加:你的 my_671b 配置 + --override.imports fused_swiglu 同时用。

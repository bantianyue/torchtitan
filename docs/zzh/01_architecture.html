3.1 实验层(experiments/)概览

4. 核心抽象及其关系

理解这五个抽象，就理解了 torchtitan 的骨架：

4.1 Configurable —— 一切皆「配置 + 构建」

  • 每个可构建类继承 Configurable（nn.Module 组件则继承 Module）。
  • 它内嵌一个 class Config(Configurable.Config)，必须用 @dataclass(kw_only=True, slots=True)。
  • config.build() 经由 __init_subclass__ 自动找回到拥有类（_owner），等价于 Owner(config=config)。
  • 带运行时对象的组件（tokenizer/dataloader/optimizer）通过 build(**kwargs) 把外部对象传进去。
# configurable.py 节选
class Configurable:
    class Config:
        def build(self, **kwargs):
            if not kwargs:
                return self._owner(config=replace(self))
            return self._owner(config=replace(self), **kwargs)

    def __init_subclass__(cls, **kwargs):
        # 强制 Config 用 kw_only + slots，并把 _owner 指向 cls
        config_cls._owner = cls

4.2 Module —— nn.Module + Configurable

Module(nn.Module, Configurable) 是所有可并行组件的基类。它带来两件事：

  • init_states()：递归初始化子模块参数 + buffer；权重共享（如 lm_head/tok_embeddings）在 Decoder.init_states 里先重新绑定再初始化。
  • parallelize(parallel_dims)：读取本模块的 sharding_config，分发状态（参数/buffer 变 DTensor），并把 forward 包成「重切分输入 → [可选 local_map] → forward → 重切分输出」。
# protocols/module.py
class Module(nn.Module, Configurable):
    def parallelize(self, parallel_dims):
        for child in self.children():        # 1. 递归子模块
            child.parallelize(parallel_dims)
        if self._sharding_config is None: return
        self._distribute_states(parallel_dims)        # 2. 参数/buffer -> DTensor(按 state_shardings)
        fn = self._maybe_wrap_with_local_region(self.forward, parallel_dims)  # 3. 包 forward
        def forward_with_redistribution(*args, **kwargs):
            args, kwargs = self._redistribute_inputs(parallel_dims, args, kwargs)   # 进 forward 前 redistribute(插通信)
            outputs = fn(*args, **kwargs)
            return self._redistribute_outputs(parallel_dims, outputs)      # 出 forward 后 redistribute
        self.forward = forward_with_redistribution

4.3 ShardingConfig / SpmdLayout —— 声明式切分

在每个模块 Config 上挂一个 sharding_config，用 SpmdLayout（按 mesh axis 名标注 Shard/Replicate/Partial）声明：状态怎么分、输入/输出怎么重切分、是否用 local_map。运行时 Module.parallelize() 把这些声明解析成真正的 DTensor placement。详见 05 模型系统 §声明式切分。

# protocols/sharding.py
@dataclass
class ShardingConfig:
    state_shardings: dict[str, SpmdLayout]    # 权重/buffer 放置:{name: {TP: S(0)}}
    in_src_shardings: dict | None          # 入参当前放置
    in_dst_shardings: dict | None          # 入参目标放置(进 forward 前 redistribute 到此)
    out_src_shardings: SpmdLayout | None   # 出参当前放置
    out_dst_shardings: SpmdLayout | None   # 出参目标放置(出 forward 后 redistribute)
    local_map: LocalMapConfig | None        # 是否包本地计算区(local_map)

# SpmdLayout = 按 mesh axis 名标注放置:
SpmdLayout({TP: spmd.S(0)})                              # 权重在 TP 轴切第 0 维(列并行)
SpmdLayout({DP: spmd.R, EFSDP: spmd.R, EP: spmd.S(0)})  # 专家权重:DP/EFSDP 复制,EP 切专家维

4.4 ModelSpec —— 把「架构 + 该用的并行/流水函数」打包

每个 config_registry 返回一个 ModelSpec，包含已选好的：

ModelSpec(
    name=..., flavor=...,
    model=model_config,            # 一个 BaseModel.Config
    parallelize_fn=parallelize_llama,   # 应用并行/AC/compile/FSDP
    pipelining_fn=pipeline_llm or None, # 仅 PP 模型需要
    post_optimizer_build_fn=None,
    state_dict_adapter=...,        # HF 权重互操作
)

4.5 ParallelDims —— 设备网格的真相来源

从 ParallelismConfig + world_size 构造，描述 dp_replicate × dp_shard × cp × tp × pp × ep 各维度，并由此 build_mesh() 出命名网格（pp/batch/loss/dp_replicate/fsdp/cp/tp/ep/efsdp）。所有并行代码都通过 parallel_dims.get_mesh("tp") 之类拿到自己那张子网格。

# distributed/parallel_dims.py
class ParallelDims:
    dp_replicate: int; dp_shard: int; cp: int; tp: int; pp: int; ep: int; world_size: int

    def build_mesh(self):            # fsdp=dp_shard*cp;efsdp=dp_shard*cp*tp//ep
        ...                          # 构命名网格 pp/batch/loss/dp_replicate/fsdp/cp/tp/ep/efsdp
    def get_mesh(self, dims):       # get_mesh("tp") / get_mesh(["dp_replicate","fsdp"])
        ...
    @classmethod
    def from_config(cls, parallelism_config, world_size): ...  # ParallelismConfig -> ParallelDims

# CLI -> 网格的桥:--parallelism.tensor_parallel_degree=2
#   => ParallelismConfig(tp=2) => ParallelDims(tp=2) => build_mesh() => get_mesh("tp")

4.6 Trainer -- 训练循环的拥有者

Trainer 本身也是个 Configurable（trainer.py:58），它的 Config 是所有组件 config 的公共容器，把模型/并行/训练部件三套 config 挂在不同字段，自己负责零整生命周期：建网格、update_from_config、apply_overrides、meta 建模、施加并行、初始化权重、建 optimizer/lr/dataloader、跑 train_step 循环、存 checkpoint。它不实现训练部件，只编排。

# trainer.py
class Trainer(Stateful, Configurable):          # 自己也是 Configurable
    @dataclass
    class Config(Configurable.Config):
        model_spec: ModelSpec            # 组件①②:模型定义 + 并行函数
        parallelism: ParallelismConfig    # 组件②:并行编排参数
        loss: ...; optimizer: ...; lr_scheduler: ...  # 组件③:训练部件(都是 Configurable)
        dataloader: ...; training: ...; checkpoint: ...; debug: ...

    def train_step(self, data_iterator):
        self.optimizers.zero_grad()
        ...                          # 预取 + 统计 valid tokens
        for microbatch in microbatches:
            loss = self.forward_backward_step(...)   # 前向 + 反向(PP 走 schedule.step)
        dist_utils.clip_grad_norm_(...)            # clip
        self.optimizers.step()               # 在本地分片上更新
        self.lr_schedulers.step()

4.7 Component -- 可插拔的训练部件

components/ 下的 loss / optimizer / lr_scheduler / dataloader / checkpoint / metrics / tokenizer 都是 Configurable（如 OptimizersContainer(Optimizer, Stateful, Configurable)，optimizer.py:78）。它们通过 Trainer.Config 的字段装配，可被 --override.imports 的 @override 工厂按 FQN 替换，不改 core。这是 torchtitan「可扩展」的另一根支柱：训练部件和模型组件一样可插拔。

# components/optimizer.py
class OptimizersContainer(Optimizer, Stateful, Configurable, Generic[T]):
    @dataclass
    class Config(Configurable.Config): ...

def default_adamw(lr=8e-4, **kwargs) -> OptimizersContainer.Config:  # config_registry 里:optimizer=default_adamw(lr=2.2e-4)
    return OptimizersContainer.Config(lr=lr, ...)

# config_registry 装配:Trainer.Config(optimizer=default_adamw(lr=2.2e-4), ...)
# --override.imports my_override 可把 default_adamw 换成自定义 Optimizer,core 不动
七个抽象如何串起来
config_registry() 返回 ModelSpec（含 model.Config 与若干 callables）→ Trainer 用 model_config.build() 在 meta 设备造出 Module 树 → 通过 model_spec.parallelize_fn 调用 Module.parallelize()，把每个模块的 ShardingConfig 落为 DTensor → ParallelDims 提供这一切所需的设备网格 → 训练循环里 Trainer 编排 Component（loss/optimizer/...）跑 train_step，部件同样 Configurable 可插拔。

5. 一次启动的请求流

把上面的抽象放进真实调用链：

# train.py
config_manager = ConfigManager()
config = config_manager.parse_args()      # tyro：--module/--config + <section>.<key>=val
trainer = config.build()                    # Trainer.Config.build() → Trainer(config)
trainer.train()                            # 训练循环（或先存种子检查点）

# Trainer.__init__ 内部（详见 02 训练流程）
init_distributed() → ParallelDims.from_config(...)

model.parallelize_fn(...)                # 并行 + AC + compile + FSDP

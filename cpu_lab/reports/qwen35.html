Qwen3.5-0.8B on torchtitan, CPU only

Where the integration succeeds, where the host runs out, and how each was measured.
The integration works; the host does not have the memory for it.
Every CPU incompatibility in torchtitan's native Qwen3.5 is closed and the model builds, shards over 8 ranks, loads the converted HF checkpoint and runs a full forward/backward of step 1 under FSDP + gloo. What stops a complete training run is the host: with no model loaded this box has 3.45 GiB of physical memory free and 15.69 GiB of commit headroom, while the fixed cost of training 0.8B - parameters, gradients and Adam's two moments, before any activation - is 12.71 GiB in fp32. Sharding spreads that cost across ranks, it does not shrink it.

1What was asked, and what came of it

Train Qwen3.5-0.8B locally with torchtitan, on a CPU-only machine, without touching anything under torchtitan/ except model directories.

torchtitan already ships a complete native Qwen3.5 - model.py, sharding.py, parallelize.py, a state_dict_adapter, and an _0_8b flavor - so no model code had to be written. The work was entirely CPU enablement, and all of it is closed (section 2), plus the plumbing around it: a model-free dataset-cache prewarm (section 4) and an HF-to-DCP weight conversion.

The 0.8B model then refuses to train here, on memory. Section 5 is the ledger and section 6 is the isolation that shows the wall belongs to the host rather than to Qwen3.5.

2Five CPU gaps, all closed

Each is a runtime shim in cpu_lab/qwen35_cpu.py, applied before torchtitan is imported, so torchtitan/ stays untouched.
#gapsymptomshim
1fla imported at module scopeqwen3_5/model.py does from fla.ops.gated_delta_rule import ...; flash-linear-attention is Triton-only and there is no CPU Triton wheel, so importing the model fails outright._install_fla_shim registers a synthetic fla package whose kernels are the chunkwise gated-delta-rule algorithm in plain PyTorch (parallel within a chunk, sequential only across chunks).
2flex attention has no CPU backwardForward works, so it fails late - at the first loss.backward() - as NotImplementedError: FlexAttention does not support backward on CPU. 6 of the 24 blocks are full attention._patch_eager_flex_attention replaces FlexAttention.forward with matmul + softmax in fp32, keeping the (B, L, N, H) contract.
3Triton-only varlen convOnly reached under the varlen backend, which is itself CUDA-only - so unreachable here, but it would half-work if the backend were ever selected._patch_causal_conv1d_varlen substitutes a per-document torch depthwise conv.
4forward needs a special_tokens batch keyOnly MMDataLoader emits it, so text-only SFT through ChatDataLoader raises KeyError: 'image_id' on step 1._patch_text_only_special_tokens supplies {'image_id': -1, 'video_id': -1} sentinels.
5create_block_mask API mismatchtorchtitan calls create_block_mask(..., separate_full_blocks=...); the pinned torch 2.12.1 signature is (mask_mod, B, H, Q_LEN, KV_LEN, device, BLOCK_SIZE, _compile). Every rank dies on step 1 with TypeError. torchtitan CI tracks PyTorch nightly, so no release torch hits it._patch_attention_mask_creation makes mask construction a no-op. The mask is already discarded by gap 2, so this removes cost as well as the crash; the cost is that attention stays purely causal.

4Two failures that looked like model bugs and were not

Both cost real time and both are now prevented by the launcher.

A dataset-cache race that presented as a training hang

All 8 ranks built the HuggingFace datasets Arrow cache concurrently. ChatDataset.__init__ calls shuffle(seed=42), which makes datasets write an indices cache - and because the seed is fixed, all 8 ranks compute the same destination path and race on it. Rank 1 died writing it (OSError: [Errno 22] Invalid argument from shutil.move); the other seven were still at Training starts at step 1 with 0% CPU, and gloo reported it 300 s later as Timed out waiting 300000ms for recv operation to complete. One dead rank, seven innocent victims, one misleading error.

cpu_lab/prewarm_dataset.py builds that cache once, single-process, and without a model: the launcher's own warmup runs a real rank, which for 0.8B means 852 M parameters plus their optimiser state in one process - more than this host has. Confirmed fixed: after the prewarm, all 8 ranks wrote their run_meta_rank_*.json, including rank 1.

A weight-tying hypothesis that the data refuted

FSDP groups the tied tok_embeddings + norm + lm_head into one unit and passes reshard_after_forward=(policy == "always"), which for the default policy is False - so that unit's all-gather is held for the whole step on every rank, and the crash was exactly at its unshard. That looked like the explanation. It is not: turning tying off (qwen35_0_8b_untied) dies at the identical _fsdp_collectives.allocate call. Worth recording because the fix that did move the failure was elsewhere.

5The memory ledger

852,985,920 parameters. The three components below are fixed - FSDP divides them across ranks, it does not reduce them - and they exclude activations, gloo buffers, the framework runtime (~0.25 GiB per rank) and any transient all-gather.

training.dtype is the lever, and it is not mixed_precision_param. mixed_precision_param sizes only FSDP's all-gather output; setting it to bf16 changed nothing (run qwen35_0_8b_smoke_bf16 dies at the same call). training.dtype sets torch's default dtype around model_config.build() (trainer.py:317), so parameters, gradients and Adam's zeros_like state all become bf16 with no fp32 master copy - halving the whole fixed cost. That is the configuration (qwen35_0_8b_bf16) which carried step 1's forward and backward to completion over 40.4 s.

6Isolating the wall from the model

If the failure is Qwen3.5's, a probe without Qwen3.5 should pass.

A model-free 8-rank all_gather_into_tensor sweep (cpu_lab/_probe_allgather.py) isolates the failure from Qwen3.5 entirely: no model, no FSDP, no checkpoint - just eight processes and a growing buffer. It fails too, and one attempt reported the reason explicitly:

RuntimeError: [enforce fail at alloc_cpu.cpp:117] data. DefaultCPUAllocator: not enough
memory: you tried to allocate 268435456 bytes.
256 MiB, refused, with no model loaded. The same sweep taken at a quieter moment reports avail_phys=0.14 GiB commit=45.63/45.63 GiB before the first attempt. So the earlier failures are the host running out of commit, and FSDP's access violation is that same exhaustion surfacing inside a native allocation, where CPU torch has no catchable OOM to raise.

8Reproducing

In order. Steps 1 and 2 are one-off; step 3 is the experiment.
# 0. the host has to be able to hold the dataset cache and the checkpoint
#    (both under D:, per the project constraint on where artifacts live)

# 1. build the HuggingFace datasets arrow cache once, single-process and
#    model-free -- 8 ranks building it concurrently is what killed rank 1
python cpu_lab/prewarm_dataset.py \
    --hf-cache D:/02_source/torchtitan/cpu_lab/hf --config qwen35_0_8b_smoke \
    --dp-world-size 8 --wipe

# 2. convert the HF weights into torchtitan's DCP layout
python cpu_lab/convert_qwen35_hf.py --input-dir qlora_lab/model \
    --output-dir cpu_lab/checkpoints/qwen35_0_8b_hf

# 3. run. --no-warmup because step 1 already built the cache.
python cpu_lab/run_cpu_train.py --combo qwen35 -n 8 \
    --module cpu_lab.qwen35 --config qwen35_0_8b_bf16 \
    --hf-cache D:/02_source/torchtitan/cpu_lab/hf --no-warmup \
    --log-dir cpu_lab/logs_qwen35/my_run

# 4. re-render this page from whatever run.json files exist
python cpu_lab/qwen35_report.py --log-root cpu_lab/logs_qwen35 \
    --out cpu_lab/reports/qwen35.html

9What would make it fit, and what is still open

Ordered by how much each is worth - all of them changes under cpu_lab/, none of them changes to torchtitan.
  • Free the host before blaming the model. Idle, this box has 3.45 GiB of physical memory free; the largest single holder is the IDE. Closing it roughly triples the headroom, which is the difference between paging and fitting.
  • Drop the vision tower for text-only SFT. It is ~100 M parameters that receive no gradient from ChatDataLoader data. parallelize.py already guards on model.vision_encoder is not None, so this is a config change in cpu_lab/, not a torchtitan change - and it removes 0.7 GiB of the bf16 budget.
  • Restore document-boundary masking. Gap 2 and gap 5 both leave attention purely causal, so packed SFT documents attend across their boundaries. Fixing it needs positions plumbed into the attention forward (the qwen3_5 full-attention layer calls inner_attention without it) plus a per-document reset of the GatedDeltaNet recurrence.
  • Raise the gloo timeout for paged runs. A step that takes 40 s resident can take minutes while paging, and the default 300 s collective timeout then fires on a run that was merely slow.

# 2026-10-13

## 换机计划取消，回到本机跑混合并行

用户反馈换机失败，只能在本机（i7-1165G7 / 4 核 8 线程 / 16 GiB / 无 GPU）继续。
诉求：给出几个**本机可用**的混合并行方法。

把 `run_cpu_train.py` 的策略预设从 TinyGPT 换到 **Qwen3.5-0.8B** 上实测，
发现三个约束是**关于模型**而不是关于机器的，把混合空间砍掉一大半。

### 三个硬约束（模型层面）

1. **PP 不能开 weight tying** —— `torchtitan/models/common/decoder.py` 在
   `enable_weight_tying and pipeline_parallel_degree > 1` 时直接
   `raise NotImplementedError`。**这是架构性的，不是 bug**：tying 让
   `tok_embeddings.weight` 与 `lm_head.weight` 是同一个 tensor，
   而 PP 把 embedding 放在 stage 0、lm_head 放在末 stage，一个 tensor 不能在两个 stage。
2. **TP 上限 = 2** —— `tensor_parallel_degree (4) must divide n_kv_heads (2)`。
   Qwen3.5-0.8B 只有 2 个 KV head，任何 rank 数下 tp 都不能 >2。
3. **TP × FSDP 有 stride bug** —— tp2 × dp_shard2 报
   `view size is not compatible with input tensor's size and stride`。**未解决**。

### `--dry-run` 不能验证多 rank（重要，别被误导）

`fake_backend` **不做任何通信**，后果分两类：

- **PP 必然死**：stage 初始化要用 P2P 交换形状元数据（`_recv_meta`），
  收不到就是垃圾形状 —— 实测 `tried to allocate 4517329193108106637 bytes`
  或 `_pickle.UnpicklingError: invalid load key`。
- **TP / FSDP / HSDP 报 `nan`**：all-reduce / all-gather 是 no-op，
  数值本来就没意义 —— `Loss is not finite (global_avg_loss=nan) at step 2`。

⇒ `--dry-run` 只能用来确认「配置能解析、mesh 能建起来」。
数值相关、以及**任何 PP，都必须真跑**。

顺带修了一个 bug：`--dry-run` 没给子进程设 `NGPU`，而 torchtitan 从 `NGPU`
（不是 `WORLD_SIZE`）读 mesh 的 world size ⇒ 任何 `-n > 1` 的干跑都报
`NGPU environment variable must be set`。已修。

### 维度排序（按每步通信量，从便宜到贵）

| 维度 | 每步传什么 | 是否分片 参数/梯度/Adam |
|---|---|---|
| **PP** | stage 边界激活（P2P） | ✅ 1/pp，且**没有全量 all-gather 缓冲** |
| **TP** | 每层激活 all-reduce | ✅ 1/tp |
| **FSDP** | **全量参数 all-gather + 梯度 reduce-scatter** | ✅ 分片，但**每 rank 固定 ~4.8 GiB 瞬态缓冲，不随 rank 数缩小** |

⇒ 内存模型对比（bf16）：
```
纯 FSDP N rank：6.83 GiB + 4.8 GiB × N     → N=4: 26 GiB（本机放不下）
PP=4, dp_shard=1：每 rank 6.83/4 + ~0.5    → 合计 ~8.8 GiB
```

**CPU 上并行的目的只有「装得下」，不是「跑得快」** —— 2 rank 实测 140 s/step
比 1 rank 的 64 s/step **慢 2.2 倍**，瓶颈是 gloo over TCP 每次 all-gather 搬
1.71 GiB。别用加速比评估，用「能不能跑完」评估。

### 本次改动（commit `aba408f40`）

- `convert_qwen35_hf.py` 加 **`--untied`**：把 `lm_head.weight` 从 embedding

  实现要点：`to_hf` 后**先删掉** `lm_head.weight` 再做 coverage 与 `dcp.load`
  （磁盘上没有这个键，不删会加载失败），load 完再 `clone()` 回来。

  + `local_batch_size=4`（batch 1 时 PP 只有 1 个 microbatch ⇒ 流水线完全串行，
  白白多付 P2P 开销）。
- `run_cpu_train.py`：干跑时给子进程设 `NGPU`。
- `cpu_lab/README.md` 新增「Hybrid parallelism on this host」章节：
  三约束表 + 维度成本表 + 两个内存模型 + 四条可直接跑的 recipe。

## 换更小模型 Qwen2.5-0.5B（494M）真跑 —— 换机失败后的本机方案

换机失败 ⇒ 回到本机。用户要求「真跑不要 dry-run」+「换成更小的 Qwen/Qwen2.5-0.5B」。

### 关键发现：torchtitan 上游**没有** qwen2_5，但可以复用 qwen3 骨架

`torchtitan/models/` 只有 `qwen3` 和 `qwen3_5`。Qwen2.5 = Qwen3 dense 减两处，
且**两处都能在现有 config 对象里表达**（无需改 torchtitan）：

1. **Qwen3 有 qk_norm**（对 q/k 做 RMSNorm），Qwen2.5 没有 →
   `make_gqa_config(..., qk_norm=None)`。**错在这里是静默的**：norm 会随机初始化，
   而所有 coverage 检查仍全绿。
2. **Qwen2.5 的 q/k/v 有 bias**，Qwen3 没有 → `Linear.Config(bias=True)`。
   但 `make_gqa_config` **不暴露 bias**，必须自己对返回的 `GQAttention.Config`
   做 `dataclasses.replace(cfg, qkv_linear=replace(..., wqkv=replace(wqkv, bias=True)))`。
   （`o_proj` 与 MLP 三个矩阵**无** bias。）

⇒ 因此 `cpu_lab/qwen25/__init__.py` 只是「构造 config + 换 adapter」，
`parallelize_qwen3` / `set_qwen3_sharding_config` / `pipeline_llm` 全部照用。

### 其他约束

- **`sdpa` 已被 torchtitan 移除**：`get_attention_config("sdpa")` 直接
  `raise ValueError`；`varlen` 是 CUDA-only ⇒ CPU 上**只能** flex + eager 反向补丁。
- **`ModelSpec` 有 5 个必填位置参数**，含 `post_optimizer_build_fn`；
  dense 模型传 `None`（照抄 llama3），漏了会 `TypeError: missing 1 required
  positional argument`。
- adapter 只需在 `Qwen3StateDictAdapter.from_hf_map` 里**追加 3 条 bias 映射**；
  `to_hf` 是 `from_hf_map` 的反向推导，自动跟进，不用改。
- **TP 上限仍是 2**（`n_kv_heads=2`），与 Qwen3.5 相同。

### 实测（本机 8 核 / 16 GiB）

| 配置 | 结果 |
|---|---|
| 单 rank bf16 随机初始化 2 步 | loss 12.4346，峰值 RSS 5.51 GiB，wall 75 s |
| 单 rank 真实权重 SFT 3 步（seq256） | loss 2.0005，峰值 4.94 GiB，wall 248 s |
| **2 rank FSDP** | **两 rank loss 逐位相同 11.502740**，每 rank 峰值 2.70 GiB，合计 5.38 GiB |

bf16 状态：494,032,768 参数 → params 0.92 + grads 0.92 + Adam 1.84 = **3.68 GiB**
（Qwen3.5-0.8B 是 6.36 GiB）⇒ 多 rank 每 rank 开销也从 ~4.8 降到 ~3.2 GiB，
所以 4 rank 从「~26 GiB 装不下」变成「~13 GiB 装得下」。**这就是换小模型买到的东西。**

### 踩坑

- **curl `--max-time 60` 会静默截断大文件**：`tokenizer.json` 期望 7,031,645 B
  实际只下到 1,232,890 B，`merges.txt` 同样被截（819,200 vs 1,671,839）。
  症状很误导——不是下载失败，而是**训练时报
  `Exception: EOF while parsing a value at line 52359 column 22`**（tokenizers 库
  解析半个 JSON）。⇒ **下载后必须比对 `Content-Length`**，不能只看 exit code。
  修法：`curl -sIL | grep -i content-length | tail -1` 取真值（302 会返回两个），
  不等就重下（`-L --retry 3 --max-time 600`）。
- `run_cpu_train.py` 有自己的 `--steps`，**不接受** `--training.steps` 透传。
- 多 rank 的 dataset 缓存竞态：启动器**自带**单进程 warmup（`-n > 1` 且未传
  `--no-warmup` 时自动跑），所以不必手动调 `prewarm_dataset.py`。

### 完整混合并行实测矩阵（Qwen2.5-0.5B，全部真跑，无 dry-run）

| combo | ranks | 结果 | 峰值 RSS/rank | 合计 |
|---|---|---|---|---|
| `qwen25`(FSDP1) | 1 | loss 12.4346（随机初始化） | 5.51 GiB | 5.51 |
| `qwen25`+SFT | 1 | loss 2.0005（真实权重） | 4.94 GiB | 4.94 |
| `qwen25`(FSDP) | 2 | loss 11.502740 **逐位相同** | 2.70 GiB | 5.38 |
| `qwen25`(FSDP) | 4 | loss 12.054090 逐位相同 | 1.84 GiB | 7.31 |
| `tp` | 2 | loss 11.542720 逐位相同 | 3.63 GiB | 7.27 |
| **`tp_fsdp`** | 4 | loss 11.877500 逐位相同 | 2.25 GiB | 9.09 |
| **`hsdp`** | 4 | loss 12.573080 逐位相同 | 2.23 GiB | 8.93 |

⇒ **TP×FSDP 在 Qwen2.5 上可用**，而在 Qwen3.5-0.8B 上会报
`view size is not compatible with input tensor's size and stride`
⇒ 那个 stride bug **不是** CPU 上 TP×FSDP 的固有缺陷，而是 Qwen3.5
(GDN/vision) 或那个规模特有的。
⇒ **PP×FSDP 卡死**：step 1 正常（loss 3.52383、grad_norm 195 跨 rank 一致），
之后完全停住，1800 s 超时也没救 ⇒ 不是超时、不是内存，是三维组合的固有阻塞。

### `checkpoint.enable=False` 会**静默禁用** `initial_load_path`（重要坑）

`CheckpointManager.__init__` 在 `if not self.enable: return` 处就返回了
（`torchtitan/components/checkpoint.py:470`），**根本不读** `initial_load_path`。
⇒ 配了 `initial_load_path` 但 `enable=False` 的配置会从随机初始化开训，
**无报错无警告**，唯一症状是 loss 从 ~12 起而不是 ~2。
本次 PP 第一次跑就是这样失败的（loss 11.93 = 随机初始化，grad_norm nan）。
⇒ `_config` 因此加了独立的 `enable_checkpoint` 参数（与 `save` 分离）。

### 另一个坑：curl `--max-time` 会**静默截断**大文件

`tokenizer.json` 期望 7,031,645 B，实际只下到 1,232,890 B；`merges.txt`
819,200 vs 1,671,839。exit code 是 0，直到训练时才炸：
`Exception: EOF while parsing a value at line 52359 column 22`（tokenizers 解析半个 JSON）。
⇒ **下载后必须比对 `Content-Length`**（302 响应会返回两个 Content-Length，
取 `tail -1`），不等就重下。已写入 `cpu_lab/README.md`。

## PP×FSDP 结论修正（2026-10-13 下午，推翻上午的「固有阻塞」判断）

上午记的「PP×FSDP 卡死、不是超时不是内存、是三维组合固有阻塞」**是错的**。
四次运行 + 两个对照实验后，真实结论：

**不是死锁，是原生崩溃 + 幸存者挂起。** step 1 永远正确，然后某个 rank 在
step 2 的 FSDP 集合通信里**原生死亡**，其余 rank 等一个已死的 peer，看起来才像死锁
——所以 1800 s 超时救不了它（超时只对还活着的 rank 有意义）。

同一配置四次运行的死法各不相同（这是它像死锁的原因）：
| 配置 | 死法 |
|---|---|
| lb=4, threads=2 | `RuntimeError: could not execute a primitive`（oneDNN） |
| lb=4 + ONEDNN_VERBOSE | `Fatal Python error: Aborted`（FSDP `all_gather_into_tensor`） |
| lb=2, threads=1 | `Windows fatal exception: access violation`（`reduce_scatter_tensor`） |
| lb=2, threads=2 | 同上 |

崩点永远是 FSDP 的梯度规约：pipelining 的 `perform_reduce_grad()` 手动调
`post_backward()` → `foreach_reduce` → `reduce_scatter_tensor`，即
`set_requires_gradient_sync(False)` 期间累积的 unsharded 梯度一次性 reduce-scatter，
是整个 step 最大的单次分配。

**根因是 commit 上限，不是物理内存。** 决定性自然实验：
- `pp -n 4`（无 FSDP）：peak commit 12.92 GiB，结束余 6.97 GiB，**avail_phys 也降到
  0.00 GiB 但跑完**（2 步，loss 3.136680，grad_norm 184 全 rank 一致）。
- `pp_fsdp -n 4`：peak commit 19.98 GiB，结束余 **0.05 GiB** → access violation。
⇒ Windows 上物理 RAM 耗尽只是换页（能活），**commit 耗尽才是硬墙**（无 catchable OOM，
表现为 whoever allocated last 里崩）。
另：`lb=2` 是 torch 允许的最小值（`microbatches must be >= stages`），且比 lb=4 **更耗**
（19.98 vs 14.18 GiB），降压要降 lb 是反向优化。

**代码路径本身没问题**：TinyGPT `pp_fsdp`×4 完整跑完 2 步（34 s，loss 跨 rank 一致、
grad_norm 全 rank 一致）。注意 TinyGPT 全程 fp32，**没覆盖 bf16/oneDNN 路径**，
所以它只证明 PP×FSDP 逻辑对，不证明 bf16 下对。

**已落地的修复**（`cpu_lab/run_cpu_train.py`）：
1. `_wait_for_ranks()`：某 rank 非零退出而其他还活着 ⇒ taskkill 杀掉幸存者，
   不再白等 gloo 超时。之前每次诊断都要耗 30 分钟。
2. `_native_crash_scan()` + `_report_native_crash()`：扫所有 rank 日志找原生崩溃签名，
   指认**真正先死的 rank**（第一个非零退出码通常是被看门狗杀的那个），并把
   per-rank 峰值 commit/RSS + 系统低水位打在崩点旁边。
3. 启动前打印宿主可用物理内存 / commit 余量。

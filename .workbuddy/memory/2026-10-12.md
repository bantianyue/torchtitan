## 复核 PP×TP×FSDP 三维组合（供用户自行执行）

对 2026-10-10 的结论做了一次完整复核，并固化「命令 + 读日志」的配方。

**命令**
```
python cpu_lab/run_cpu_train.py --combo pp_tp_fsdp -n 8 --sp false
```
等价并行度：`world_size=8 = dp_shard(2) × tp(2) × pp(2)`，cp=1、dp_replicate=1。
默认 config = `tinygpt_pp`（`8L512_untied`，27,542,528 参数；
local batch 8 / global batch 16 / seq 128 / Interleaved1F1B，4 stages、8 microbatches）。

**实测（2026-10-12）**
- 3 步总耗时 112.5s；启动约 50s（含 8 rank × 5s 错峰），每步约 7–8s。
  默认 steps=20 约 3.5 分钟。
- 末 stage 的 4 个 rank（4–7）loss 完全一致：8.08627 → 6.06258 → 7.76089。
- **前 4 个 rank（0–3，非末 stage）loss 记哨兵 `-2.00000`**，不是真实 loss。
- `grad_norm` **8 个 rank 全部相同**（step3 = 12.3918），因为裁剪在 PP mesh 上同步。

**读日志要点（这条要固化，容易看错）**
- 每 rank 一个文件：`cpu_lab/logs/rank_<i>.log`（单进程运行为 `train.log`）。
- 真实 loss 只在**最后一个 PP stage** 的 rank 上；其余为负哨兵。
  怎么快速找末 stage：看 `Building device mesh with parallelism: pp=..` 之后的
  microbatches/stages 行，或直接扫所有 rank 取非负 loss 的那组。
- 校验正确性：`grad_norm` 全 rank 一致 + 末 stage 组内 loss 逐位相同。
- 该组合下 loss 抖动大（每步只 8 条、128 token），3 步看不出趋势，需更多步。

## 追加：初始权重来源 + SFT 流程（用户提问，已实证）

### 初始权重 = 进程内随机初始化，没有任何权重目录
- `Trainer.__init__` 调 `model.init_weights()` → `Module.init_states()`，按各子 Config 的
  `param_init` 抽样（定义在 `torchtitan/models/tinygpt/__init__.py`：
  `_LINEAR_INIT` trunc_normal(0.02)、`_TOKEN_EMB_INIT` normal(0.02)、
  `_POS_EMB_INIT` normal(0.01)、`_NORM_INIT` ones/zeros、
  `_depth_init` 深度缩放、`_output_linear_init`）。
- 实测：`wq.weight` std=0.02004、`pos.weight` std=0.00998、`norm.weight` mean=1.0
  —— 与声明分布一致，确认是随机初始化。
- 日志里那句 `initial_load_model_only=True has no effect without an initial_load_path`
  就是"没加载任何预训练权重"的证据。
- **加载不了 HF 的 coderian/TinyGPT 权重**：`ModelSpec.state_dict_adapter = None`，
  且本模型省了 GPT-2 的 linear bias，键名/形状都对不上。要加载必须写 adapter，
  或用本模型自己存的 ckpt 走 `checkpoint.initial_load_path`。

### 从头训练 vs SFT：同一套代码，只换 dataloader
- 同一个 `Trainer`、同一个 `ModelSpec`、同一个 loss 类、同一套并行参数、
  **同一个启动脚本**（`python -m torchtitan.train --module ... --config ...`）。
- 差异只在两处：
  1. **dataloader**：`HuggingFaceTextDataLoader`（c4_test，全 token 都是 target）
     ↔ `ChatDataLoader`（chat 对，**prompt token 置 IGNORE_INDEX**）。
     掩码无需改 loss：`cross_entropy_loss` 里 `ignore_index=IGNORE_INDEX` 是**硬编码**的。
  2. **初始权重**：随机 init ↔ `checkpoint.initial_load_path` 指向预训练 ckpt
     （`initial_load_model_only=True` 默认只载模型）。
- 已给 TinyGPT 加 `tinygpt_sft` 配置（`ChatDataLoader` + `tests/assets/sft_test/data.json`，
  10 条 GSM8K 风格样本），单卡实测可跑（loss 7.70→6.69→5.47）。
- **必须记住的 caveat**：`ChatDataset` 会贪心打包多条文档进同一序列，正确性依赖
  **document mask**；而 TinyGPT 用 SDPA（只有 `is_causal=True`），
  能表达该 mask 的 flex/varlen 后端恰好是本模型用不了的（无 RoPE、flex 无 CPU 反向）。
  → 流程有代表性，打包掩码没有。
- seq_len 受**学习式位置表**上限约束（debugmodel 是 256），不像 RoPE 可外推。

### 顺带修掉
`run_logging` 的 data 段原只认 `DATASETS` 注册表（`dataset` 字段），
对 `ChatDataLoader`（`dataset_path` + `load_dataset_kwargs`）显示成
"not in DATASETS registry"。已改为两种形状都识别，SFT 会打印数据文件绝对路径、
split、以及 `prompt -> IGNORE_INDEX` 掩码提示。

### 权重落盘位置与格式（已实测）
- 路径 `cpu_lab/outputs/<combo>/checkpoint/step-N/`（`folder` 默认 `checkpoint`，
  dump_folder 由启动器传 `--dump-folder cpu_lab/outputs/<combo>`）。
  不用启动器时默认是仓库根的 `./outputs`。
- 格式是 **DCP**：`.metadata` + `__<rank>_<x>.distcp`，**每 rank 一个分片**。
  不是 safetensors、也不是 `.pt`，`torch.load` 读不了。
- 读回方式（已跑通，单进程也可）：
  ```python
  sd = model.state_dict()
  dcp.load(sd, checkpoint_id=ckpt_dir)   # torch.distributed.checkpoint
  model.load_state_dict(sd)
  ```
  单进程会 warn "torch.distributed is disabled ... assuming single process"，无害。
- 配置是 `last_save_model_only=True` + `interval=steps` → **只存最后一步、只存模型**
  （无 optimizer / dataloader 状态）。
- 因 `state_dict_adapter = None`，`last_save_in_hf` 不可用 → 导不出 HF safetensors。
  要与 HF 互换须先写 adapter。

### 8 卡 pp_tp_fsdp 10 步基准（实测，用于日后回归对比）

loss 7.88697 → 4.05739（单调下降，仅 step9 微升）；grad_norm 26.76 → 3.22，**全 8 rank 同值**；

### 通信采集：为什么必须两层
单层 hook 一定漏。**实测**得到的 5 条结论（每条都改变了代码）：
1. FSDP2 的 all-gather 走 **Python 的 `dist.all_gather_into_tensor`**，reduce-scatter
   走 `dist.reduce_scatter_tensor`；后者会**再派发到 aten `c10d._reduce_scatter_base_`**
   → 不去重就会把一个集合通信数两遍。用「Python 包装在栈上时抑制同 bucket 的 aten 算子」解决。
2. `fsdp.all_gather_copy_in` 是**本地 staging 拷贝**，不走网 → 必须排除，否则 FSDP 的
   all-gather 字节数虚高约 50%。
3. PP 的 P2P **不调 `dist.batch_isend_irecv`**：torch 的 stage 对 homogeneous batch 走
   `dist.isend/irecv` 快路径。而 `isend/irecv` **不能包**——`P2POp.__new__` 用
   `op not in [isend, irecv]` 做同一性检查，包了 PP 立刻 `ValueError: Invalid op`。
   → 改在 `dist.P2POp.__new__` 计数（公共 API，不改任何 identity）。
4. PP 的梯度裁剪走**纯 Python `torch.distributed.all_reduce`**（`distributed/utils.py:646`），
   不经 dispatcher → 只看 dispatcher 会把 PP 报成「没有任何 all-reduce」。
5. **单卡运行时唯一出现的集合通信是存 checkpoint**：DCP 的 `scatter_object_list`
   实现为 rank0 broadcast（`checkpoint.py dcp_save` → `state_dict_saver` → `utils.reduce_scatter`）。
   → 必须按 phase 分类：`step` / `init` / `checkpoint`，否则会把存盘 I/O 当训练带宽。
   查这类「不知道谁发的」用 `CPU_LAB_COLLECTIVES_STACK=1` 记录首次调用栈，别猜。

### 实测流量（每 rank 每步，仅训练步内）
| 策略 | all-gather | reduce-scatter | all-reduce | P2P |
|---|---|---|---|---|
| fsdp (2) | 9 次 3.74 MB | 5 次 4.33 MB | 4 次 24 B | — |
| tp (2, SP off) | — | — | 12 次 591 KB | — |
| tp (2, SP on) | 18 次 590 KB | 18 次 1.18 MB | 22 次 142 KB | — |
| pp (2) | — | — | 1 次 4 B | 26+26 次 6.29 MB |
| pp_tp_fsdp (8) | 5 次 13.7 MB | 5 次 27.0 MB | 77 次 18.0 MB | 24+24 次 6.0 MB |

- FSDP 每步 gather 的字节约为分片参数的 **2 倍**（backward 前要重新 gather）。
- all-reduce 只有 12 B = 3 个 fp32 = 梯度范数 → 一眼区分「同步」与「真流量」。
- SP 打开后 all-reduce **不会降到 0**（分片的 norm 仍需一次），只多了 all-gather+reduce-scatter。
- 三维组合下各 rank 总量不同：rank0–3 是 4.15 GB / 60 步，rank4–7 是 3.95 GB
  （stage 角色不同），所以必须每 rank 各自 dump。

### 植入语料推理验证（证明训练真的生效）
做法：造一个只含 2 个虚构暗号的语料（3001 行），训练后**在另一个进程**用 DCP 载回
checkpoint，对比随机初始化权重。实测：
- 单卡 300 步：p(暗号) 1.5e-56 → 0.914，逐 token 准确率 0.13 → **1.00**，贪心输出与暗号逐字一致。
- 8 卡 pp_tp_fsdp 60 步（loss 0.152）：p 8.6e-51 → 0.608，准确率 0.00 → **1.00**，两个暗号都 EXACT MATCH。
- 副产品：证明 8 个分片能被单进程完整合并 → 是一个真实的 checkpoint 读取测试。

**两个会误判成「权重没训好」的探针坑（都踩过）**：
1. **不要无条件把 `lm_head` 重绑到 embedding**。tied 模型这行无害；但 PP 用的都是
   **untied** flavor，这行会把训练好的输出头换成 embedding 矩阵 → 模型输出噪声
   （`\xda\xda\xda…`）而加载报告一切正常。要读 `enable_weight_tying` 判断。
2. **prompt 要带 BOS**。语料是 `[BOS] + text`、position 从 0 起；探针从 position 0 开始
   问，就等于把问题提前了一个位置。8 卡 ckpt 上这一条就是 0.87/0.93 与 1.00/1.00 的差别。

### 其他踩到的坑
- **数据集目录里不能放 `manifest.json`**：`load_dataset(<dir>)` 会把目录下所有文件当数据、
  推断同一套 schema，报 `An error occurred while generating the dataset`（真因
  「column names don't match」）。manifest 已移到 `cpu_lab/probe_manifest.json`。
- **`--dataloader.dataset-path` 可以覆盖数据目录**，但 dataset **name 仍是注册表键**
  （`_validate_dataset` 是 `dataset_path or config.path`）→ 报告/banner 必须打印**实际用的路径**
  并标注 overridden，否则会写错目录。
- **checkpoint 的 interval 来自配置自己的 `steps`**，`--steps` 只改训练步数不改间隔：
  用 `tinygpt_pp`（steps=20）跑 `--steps 60` 会额外存 step-20/40 两个**完整** ckpt
  （含优化器状态，每分片约 40 MB），最后一步才是 model-only（约 13 MB）。
- **沙箱的批量删除守卫**：`rm -rf` 超过约 50 个文件会被拦（`SAFE_DELETE_BULK_CONFIRM_REQUIRED`），
  连 `dangerouslyDisableSandbox` 也拦。清目录改用启动器自己的 `_clear_outputs`，
  或 `--log-dir` 换目录，不要 `rm -rf`。这条只在沙箱里出现，用户本地 cmd 没有。
- `head`/`grep` 管道会让后台任务的输出看起来「秒退且只有几行」，实际是管道提前关闭；
  要判断成败请把输出重定向到文件再读。

### 预热（prewarm）一直静默失败（已修）
`_prewarm_dataset` 把预热当普通 run 跑，但**没清自己的 dump 目录** `outputs/_warmup`，
于是从第二次运行起预热就 resume 并报 `Missing key in checkpoint state_dict:
dataloader.dp_rank_0`。启动器把预热失败当非致命（它只是优化）→ **静默**。
后果很隐蔽：没有预热好的缓存，N 个 rank 就并发自建缓存 → 偶发卡死（正是预热要防的事）。
修法：预热前清 `outputs/_warmup`，并给预热加 `--checkpoint.no-enable`。
**回归判据：同一条命令连跑两次，两次都要打印 `dataset cache ready`。**
（该失败曾让我误判为「8 卡 pp_tp_fsdp 挂了」，实际上训练本身没问题。）

## 缩放阶梯实测：这台机器能跑多大（含失败边界）

**机器**：16 GB 物理内存 / 8 核 / commit 上限 40.75 GiB（跑大模型时 Windows 自动撑到
43.88 GiB，能撑多大受系统盘 C: 剩余 13.4 GiB 限制）。
**策略固定** `pp2 × tp2 × dp_shard2`（8 rank，`--sp false`），seq 128、local batch 8
（global batch 16、2048 token/step）。

| flavor | N | s/step | RSS/rank | commit/rank | 8 rank commit 合计 |
|---|---|---|---|---|---|
| `8L512_untied` | 27.5M | 6.5 | 0.55 GiB | 0.66 GiB | 5.16 GiB |
| `scale_12L768` | 88.5M | 15.0 | 0.77 GiB | 0.94 GiB | 7.44 GiB |
| `scale_16L1024` | 206.1M | 36.5 | 1.00 GiB | 1.50 GiB | 12.01 GiB |
| `scale_24L1536` | 687M | — | — | — | **崩在 FSDP all-gather 分配** |

**三点线性拟合（全部 R²≈1）**
- commit（8 rank 合计）= **41.2 B/param × N + 4.08 GiB**
- 驻留 RSS（8 rank 合计）= **20.3 B/param × N + 3.35 GiB**
- 每步耗时 = **0.170 s / M 参数 + 1.1 s**
→ commit 口径上限约 **232M**，驻留口径上限约 **364M**（取小：~232M）。
→ 结论：截距（每 rank 固定 ~0.5 GiB × 8）主导，**减 rank 数比缩模型更能抬高天花板**；
时间才是"能不能用"的判据：206M 只有 2048/36.5 ≈ **56 token/s**。

**实测边界**：206M 能跑完；687M 在第一个 forward 的 unshard 就崩，末 stage（rank 5–7）
报 `Windows fatal exception: access violation`（`fsdp_collectives.py:59 allocate`），
首 stage（rank 0–4）停在 `Training starts` 等对端，直到超时。

### 本次修掉的三个坑（都会让结论错）
1. **`run_meta_<rank>.json` 的 `local_params` 是 DTensor 的 `numel()` → 返回全局形状**，
   pp2×tp2×shard2 下每 rank 报 N/pp，8 rank 求和 = **4N**。当参数量用会把外推结果缩小 4 倍。
   → 改为解析 torchtitan 自己的 `Model <name> <flavor> size: N total parameters` 行
   （那行在任何分片之前打印）。求和只作兜底，且报告里注明数据来自哪一路。
2. **commit 预算不能在报告时刻实时读**：在跑的 run 会把 `commit_used` 顶满（实测把预算
   压到 1.54 GiB，外推得 0M）。改用各档 `system_after` 快照里的**最小** `commit_used` 当

3. **跑挂的档不会写 `run.json`，会被静默跳过**——而它恰恰是最有价值的点。
   新增 `collect_failed()`：目录里有 rank 日志但没有 `run.json` 就按日志特征归类
   （`access violation` / `MemoryError` / 超时），并在报告里单列一节。
   注意 **Windows 上大分配失败不一定抛 `MemoryError`**，而是 access violation 直接崩。

## 晚 · qlora_lab：Qwen3.5-0.8B 在纯 CPU 上做 LoRA 微调

### 目标与决策
用户要「跑 qwen-3.5 0.8B 4bit量化 本地训练」。核查后**去掉 4bit**：
- CPU 上 bnb 4bit = 先反量化成 bf16 再算，比原生 fp32 **更慢**；0.8B fp32 仅 ~3.4 GB，
  16 GB 内存本来就装得下。QLoRA 的价值是省显存，在内存富裕的 CPU 上省不出东西。
- 改成「LoRA + 权重不量化」，靠**主干冻结**省内存。
- **torchtitan 干不了这件事**（预训练框架：无 HF 权重加载、无 PEFT、无量化）
  ⇒ 在仓库根建 `qlora_lab/`（与 `cpu_lab/` 平级），**不改 `torchtitan/` 任何代码**。
- 另建独立 `.venv`，不污染 `cpu_lab` 用的那个 torchtitan venv。

### 关键事实
- **Qwen3.5 需要 `transformers >= 5.2.0`**（架构 tag `qwen3_5`，PR 2026-02-09 合入，v5.2.0 发布）；
  实际装到 5.19.0。
- `Qwen/Qwen3.5-0.8B` 非 gated、Apache-2.0、13 文件 1.65 GiB；**没有 `-Instruct` 后缀**，
  post-trained 版就叫这个名字（`-Base` 是另一个仓）。
- 权重是**单个 1.747 GB 文件** `model.safetensors-00001-of-00001.safetensors` + `.index.json`。
- 结构 `Qwen3_5ForConditionalGeneration`（text_config + vision_config 双塔）：
  主干 752.4M + 视觉塔 100.6M + lm_head(tied 不计) ⇒ **去重后 852.99M**。
  hidden 1024 / 24 层 / vocab 248,320 / head_dim 256 / max_pos 262,144。
- **24 层不是同一种层**：`layer_types` 按「线性注意力×3 + 全注意力×1」循环（18+6）。

  全注意力层名 `self_attn.{q,k,v,o_proj}`。**LoRA 必须按真实层名挂**，`in_proj_a/b`
  输出仅 16 维必须排除。

## Qwen3.5-0.8B 用 torchtitan 在 CPU 上跑通（20:00–20:50）

### 结论（一句话）
**torchtitan 原生就带 Qwen3.5 实现（含 `0.8B` flavor），不需要新增模型代码**；
只需一层 CPU 兼容补丁。**单 rank 已跑出真实 loss 并完成两步训练**；
**多 rank FSDP 跑不起来，卡在宿主的 commit 预算，不是 gloo/FSDP 的 bug。**

### torchtitan 侧的关键事实
- `torchtitan/models/qwen3_5/` 是**上游完整实现**（`model.py` 865 行 + vision tower）。
  用全限定路径 `--module cpu_lab.qwen35` 加载自定义 config_registry 即可，无需注册。
- `_0_8b` 里那句「torchtitan 不支持 tied embedding」**是过时的**：`Decoder.Config.enable_weight_tying`
  已实现，`state_dict_adapter` 也有对应的省略分支。HF 的 `tie_word_embeddings=true`
  ⇒ 磁盘上没有 `lm_head.weight` ⇒ **不开 tying 就连 `dcp.load` 都过不去**
  （`Missing key in checkpoint state_dict: lm_head.weight`），而且省掉 254M 参数
  （= fp32 下 1 GiB 权重 + 1 GiB 梯度 + 2 GiB Adam）。
- **`training.dtype` 与 `mixed_precision_param` 是两回事**：前者在 meta 构建期
  `torch.set_default_dtype`，把参数/梯度/Adam 全部变成该 dtype（无 fp32 主副本）；
  后者只改集合通信/前向的 dtype。省内存必须用前者。

### `cpu_lab/qwen35_cpu.py` 的五个补丁（都是运行时 monkeypatch，不碰 `torchtitan/`）
1. `fla` 桩（模块级 `import fla.ops.gated_delta_rule`）+ 纯 torch 分块 GDN + 因果深度卷积。
2. `FlexAttention.forward` → eager 因果实现（CPU 无 flex 反向）。
3. `_causal_conv1d_varlen` → 纯 torch。
4. 文本-only 批补 `special_tokens` 哨兵（否则 `ChatDataLoader` 走 `KeyError: 'image_id'`）。
5. **`create_block_mask(..., separate_full_blocks=...)` → 去掉该 kwarg**：
   torchtitan 跟 PyTorch nightly，本机 pin 的 2.12.1 没有这个参数。
   注意 `decoder.py` 是**按名字 import** `create_attention_mask` 的，所以补丁要打在那个名字上。

### 实测数据（务必记住）
- HF→DCP 转换：**594 张量 / 4.43 GB**，落在 `cpu_lab/checkpoints/qwen35_0_8b_hf`，
  15 个丢弃键全是 `mtp.*`（Multi-Token Prediction，torchtitan 未实现）。
- 参数：dense 752,393,024 + vision 100,592,896 = **852,985,920**（tied）。
- **单 rank bf16 / seq 128 / batch 1：64 s/step，loss 12.81853 → 12.84252，
  grad_norm 91.0 → 87.0。** 峰值 RSS 6.47 GiB、commit 11.68 GiB。
- 4 rank bf16 同一配置：forward+backward 全过，**死在 FSDP 梯度 reduce-scatter**，
  4 个 rank 同时 `access violation`；峰值 commit 合计 19.67 GiB。

### 根因：commit 预算，不是内存墙也不是 gloo bug
- 本机 commit 上限 **45.63 GiB**，**桌面基线常驻 ~25–30 GiB**（进程工作集合计才 3.5 GiB，
  差额是 committed-but-not-resident）。
- 单 rank 跑的时候实测 `avail_phys` 最低到 **0.01 GiB（9.5 MB）**、commit 只剩 4.61 GiB。
  ⇒ 单 rank 已经是贴地飞行；4 rank 要 19.67 GiB，**必然越过 45.63 上限**。
- 原生崩溃的形态**随运行随机变化**（access violation / oneDNN `could not execute a primitive`
  / gloo 300 s 超时），这正是「分配失败在不检查错误的 native 代码里」的特征，
  **不要按形态去猜具体 bug**。
- 用纯 gloo 探测排除传输问题：**all-gather 到 0.5 GiB/rank、reduce-scatter 到 1.5 GiB 输入全部正常**
  （`cpu_lab/_probe_allgather.py`、`cpu_lab/_probe_reducescatter.py`）。
  探测时如果 `avail_phys` 读出来极低，**先看是不是探测进程自己占的**——
  8 个探测进程能把 45.63 GiB commit 吃光，据此得出的「内存不足」结论是假的。

### 启动器改动（`cpu_lab/run_cpu_train.py`）
- 内存采样器新增**运行期系统最低水位**（`system_low`：`min_avail_phys`/`min_commit_free`/

  理由：per-rank 峰值合计只回答「这个 job 多大」，回答不了「它装得下吗」——
  宿主是共享的，同一个 job 在高基线时会死、在低基线时会活。**这个指标一加就当场定位了根因。**
- 失败路径也要写 `run.json`/`summary.txt`（此前崩溃时内存数据被丢弃，恰好是唯一关心的那次）。

## 多 rank FSDP：找到真因了（21:25，推翻此前结论）

**真因是集合通信超时，不是内存。**
`Trainer.Config.comm` 默认 **init 300 s、之后收紧到 100 s**。加速器的语义是
「100 s 没完成就是挂了」；但分页的 CPU rank 一次 all-gather 合法地要几分钟，
而「第一步之后收紧到 100 s」保证后续每步都超时。

对照实验（bf16 / seq128 / batch1）：
- 2 rank + 默认超时 → rank_1 `Timed out waiting 300000ms for send operation`
- **2 rank + 1800 s 超时 → 两步全过，distinct loss=1、distinct grad_norm=1**
- 崩时 commit 还余 **2.08 GiB** ⇒ 不是内存耗尽
- 4 rank（1800 s 也崩）→ `access violation`，低水位 commit 余 **0.47 GiB**（真撞顶）

**为什么 1 rank 能过**：它同样把 `avail_phys` 压到 0.01 GiB（一直在换页），
只是**没有集合通信 ⇒ 没人能给它超时**，所以它只是慢，不会崩。

**为什么 rank 越多越糟**：FSDP 只分片参数/梯度/优化器状态，
每 rank 另有 **~1.1 GiB 不可分片开销**（Python+torch 运行时 ~0.5 GiB +
all-gather 输出与展平梯度缓冲 ~0.6 GiB @bf16），这项乘以 rank 数。
⇒ 本机 **2 rank 是甜点；4 rank 在天花板上；8 rank 不可达**。

改法：`CommConfig(init_timeout_seconds=1800, train_timeout_seconds=1800)`，
或 CLI `--comm.init_timeout_seconds 1800 --comm.train_timeout_seconds 1800`。
已加配置 `qwen35_0_8b_bf16_multi`（验证通过）。

**无效手段（别再试）**：`PYTORCH_CPU_ALLOC_CONF=expandable_segments:True`
在 torch 2.12.1 上静默接受但无效（仅 CUDA）。分配 churn A/B 实测无差异。

**关于换 32 GB 机器的判断**：值得，但要分清两个量——
- **物理内存决定能不能用**（现在 15.73 GiB、空闲仅 ~4.5 GiB，而 4 rank 驻留需 ~7.4 GiB
  ⇒ 必然抖动 ⇒ 超时 ⇒ 全崩）。32 GiB 下 4/8 rank 驻留（~8–15 GiB）能放下，抖动消失。
- **提交内存只决定会不会硬崩**。页面文件在 **C:（仅剩 11.13 GiB）**，
  换机后若仍系统托管在快满的 C: 上，上限约 32+30 ≈ 62 GiB；够用，但
  **别指望靠页面文件补物理内存**——它不增加物理内存，只会让抖动更慢。
- 建议：换机后把页面文件**放到 D:（空闲 510 GiB）并设固定大小 32 GiB**。

## 8 rank 实测与「换 32 GiB」的答复（21:35）

**8 rank 纯 FSDP 在 16 GiB 上崩了**（`logs_qwen35/bf16_multi_8r`）：日志停在
`Applied FSDP to the model`（21:31:29），之后进程全部消失，无 traceback。
与内存模型预测吻合：6.83 GiB 状态常量 + 8 × ~4.8 GiB/每 rank 不可分片开销
≈ **45 GiB，正好贴到 45.63 GiB commit 上限**。

**每 rank 不可分片开销 ≈ 4.8 GiB 的构成**（bf16，852.99M 参数）：
- all-gather 输出缓冲 = 全量未分片参数 = 1.71 GiB
- 展平梯度缓冲（reduce-scatter 用）= 1.71 GiB
- Python + torch/oneDNN 运行时 ≈ 1.4 GiB

**关键区分（这是回答「8 卡」的核心）**：
- **纯 FSDP 的 dp_shard 不缩小上面两项缓冲** ⇒ 8 rank 纯 FSDP ≈ 45 GiB，32 GiB 也贴顶。
- **PP/TP 会真正缩小**：pp2×tp2 下每 rank 的 FSDP 单元只剩 1/4 层 → 缓冲降到
  0.43 + 0.43 GiB ⇒ 每 rank ≈ 2.3 GiB ⇒ **8 rank pp2×tp2×dp2 ≈ 25 GiB**。
  ⇒ **32 GiB 跑 8 rank 必须带 PP/TP 维度，不能只用 dp_shard=8。**

**速度才是「值不值」的判据**（实测）：
- 1 rank bf16 = **64 s/step**
- 2 rank（放宽超时后跑通）= **~140 s/step，慢 2.2 倍**
- 原因：gloo/TCP 每次 all-gather 1.71 GiB，还要 8 个进程在 8 核上抢 CPU 与内存带宽。
  多 rank 增加的是通信，不是算力。

⇒ 给用户的结论：**32 GiB 能让 8 rank 跑起来，但不会更快；正确用法是 4 rank
（pp2×dp2 或 dp_shard4）+ 每 rank 2 线程。**

**为什么不用 Git LFS**：免费额度 10 GiB 存储 / 10 GiB 月流量，权重就 6.6 GiB，
且上传比从 `hf-mirror.com` 重下更慢。

**备选（若两台机器物理可达）**：`robocopy` 整目录直传最省事，连 HF 权重都不用重下；
但 Windows venv 含绝对路径，**仍应重建而非复制**。

**工具坑补充**：本机 PowerShell 安全策略禁止 `cmd.exe` 和 `[Diagnostics.Process]::Start`；
且 `git push` 用 PowerShell 管道捕获输出会得到**空 stderr**（实测误报 exit 128）。
⇒ **git / 任何需要看输出的长命令，改用 Bash 工具 + 绝对路径**，
且含空格路径必须 `"$VAR"` 加引号（否则被 word-split 成 `/d/Program`）。

# 2026-10-10

## 新增 TinyGPT 模型 + CPU 并行策略实验台

**任务**：基于 torchtitan 跑 https://huggingface.co/coderian/TinyGPT 这个极小 GPT-2 模型，
保留 FSDP/TP/PP/CP 并行策略，用于学习训练流程与并行组合。
**硬约束**：`torchtitan/` 下只能在 `models/` 新增 `tinygpt/`；禁止改动其他目录。

### 交付
- `torchtitan/models/tinygpt/`：`model.py` / `sharding.py` / `parallelize.py` /
  `__init__.py` / `config_registry.py` / `README.md`（新增，未改任何已跟踪文件）
- `cpu_lab/`：`run_cpu_train.py`（策略 preset 启动器）/ `cpu_lab_child.py` /
  `cpu_compat.py`（运行时补丁）/ `no_libuv_patch.py` / `README.md`

### 关键决策
- **不改 `models/__init__.py`**：用全限定路径 `--module torchtitan.models.tinygpt`，
  ConfigManager 会自动试 `f"{module}.config_registry"`，因此无需注册进 `_supported_models`。
- **继承 `Decoder`**，只覆写三处依赖 RoPE 的成员：`Config.max_seq_len`、
  `Config.update_from_config`、`get_attention_masks`（返回 None）。复用其 `forward`/
  `init_states`/权重绑定/PP 的 None 守卫。
- **不用 `GQAttention`**（硬依赖 RoPE）、**不用 `FeedForward`**（是 SwiGLU 三线性）。
  自写 MHA（`ScaledDotProductAttention`）+ GELU MLP。位置编码用学习式绝对位置。
- **Linear 一律 `bias=False`**：rowwise 侧的 bias 需要按 TP degree 缩放，否则每个 rank
  各加一次。`ScaledBiasRowwiseLinear` 在 DTensor 输入下会 "mixed Tensor and DTensor"，
  且它要求 local 输入。与仓库内 `FeedForward`/`GQAttention` 惯例一致。
- **token 与 position embedding 合成一个 `TinyGPTEmbedding` 模块**（子模块 `.tok`/`.pos`）：
  PP 的 `_split_module` 只保留已知 FQN（`tok_embeddings`/`layers.*`/`norm`/`lm_head`），
  独立兄弟模块会被丢弃。
- **PP 用解绑权重**：`Decoder.Config.update_from_config` 明确拒绝 tying+PP。
  PP 还需 ≥2 virtual stage/rank，故 PP 配置用 8 层 flavor（4 层只有 6 个有效节点，装不下
  `pp_degree*2` 个 stage）。
- **PP 必须 `Interleaved1F1B`**：torchtitan 用 `step(arg_mbs=...)` 驱动，只有
  multi-stage 家族实现该 API；默认 `"1F1B"` 是 single-stage，签名不匹配。

### 环境结论（CPU-only torch 2.12.1+cpu / gloo）
可用：`single`、`fsdp`、`tp`（SP 开/关）、`tp_fsdp`、`tp_sp`。
被封：`pp`/`pp_tp`/`pp_fsdp`（torch 2.12 `schedule.step()` 签名与 torchtitan 的
`arg_mbs` 约定不符）、`cp`/`tp_cp`（CPU SDPA 无 DTensor 分片策略）、`hsdp`
（gloo functional collectives 挂住）。已用官方 llama3 交叉验证 PP 失败同为环境问题。

### 踩过的坑（复用价值高）
1. Windows CPU torch 无 libuv → `TCPStore` 必须显式 `use_libuv=False`，`USE_LIBUV=0`
   环境变量在 C++ 层不被采纳。
2. `torchtitan.tools.utils` 导入时快照 `device_type`（`_get_available_device_type() or "cuda"`）。
   在**导入 torchtitan 之前**包住 `torch._utils._get_available_device_type` 返回 `"cpu"`，
   可一并修好 DeviceMesh 与 gloo backend 选择。
3. `models/common/attention.py` 在**模块级**调 `torch.compile` → 拉入 inductor → 需要 triton。
   CPU 上把 `torch.compile` 降级为 eager 透传。
4. FSDP 梯度除法用 NCCL 专有 `ReduceOp.PREMUL_SUM`，gloo 拒绝 → 包 `apply_fsdp_after`
   对所有 FSDP 模块 `set_force_sum_reduction_for_comms(True)`。
5. **8 进程同时准备 HF dataset 会争抢锁并挂住**，其它 rank 随后报 gloo 超时（看起来像训练 bug）。
   解法：每个 rank 独立 `HF_HOME`/`HF_DATASETS_CACHE` + 启动错峰 `--stagger 2`。
6. 正确性判据：TP 不分片 batch，**所有 rank 的 loss 必须逐位相同**（实测 TP-8 全 rank
   step2 = 7.54181）。

### 实测
| preset | 并行 | global batch | 结果 |
|---|---|---|---|
| single | 无 | 1 | 8.91 → 7.92 → 6.30 |
| fsdp | dp_shard=8 | 8 | 11.37 → 8.37 → 7.26 |
| tp | tp=8 | 1 | step2 = 7.54181（8 rank 全同） |
| tp_sp | tp=2 × shard=4 + SP | 4 | 10.40 → 8.20 |
| tp_fsdp | tp=2 × shard=4 | 4 | 9.997 |

注意：`local_batch_size=1` 时 global batch 随 DP 度变化，**跨策略的 loss 不可直接比较**，
要对比须先对齐 global batch。

## 追加：PP 打通 + HSDP/CP 边界厘清

### PP 已解决（新增第 7 个补丁）
torch 2.12 的 `schedules.py` 里所有 `step()` 签名都是
`step(*args, target=None, losses=None, return_outputs=True, **kwargs)`（**整批**入口，
自己切 microbatch），而 torchtitan 传 `step(arg_mbs=...)` → `arg_mbs` 落进 `**kwargs`
被当模型输入。

**但 microbatch 级入口仍在且签名正好匹配**：
`_step_microbatches(arg_mbs, kwarg_mbs, target_mbs, losses, return_outputs)`。
→ 在 `cpu_lab/cpu_compat.py` 加 `_patch_pipeline_schedule_step()`：包
`pipeline_parallel._build_pipeline_schedule`，对返回的 schedule **实例**装一个
`step` 适配器（接受 torchtitan 的关键字 → 直接调 `_step_microbatches`），并复现整批
`step` 的两项簿记（各 stage `has_backward`、`clear_runtime_states`）。
`_prepare_schedule_with_comms` 无需重放——各具体 schedule 在 `__init__` 已调用。
`loss_kwargs` 在 `_step_microbatches` 也没有槽位 → 改为绑定进 loss fn
（包装 `_build_pipeline_schedule` 时插入一个可变 holder，每步填充）。

关于「升级 torch 是否可行」：torchtitan 的 CI 直接复制 PyTorch CI 的 docker 文件
（`.ci/docker`），即跟随 **PyTorch main/nightly**，并未 pin 某个 release。
所以「升级到某版本」并不明确，且本机还得有对应 CPU wheel。适配层让这个问题不再相关。

### 实测（新增）
| preset | 并行 | 结果 |
|---|---|---|
| pp | pp=4 | 末 stage 7.85082 → 4.99697 |
| pp_tp | pp=4 × tp=2 | 末 stage 8.09366 |
| pp_fsdp | pp=2 × dp_shard=4 | 末 stage 8.08705 |
| pp_tp_fsdp | pp=2 × tp=2 × dp_shard=2，**必须 --sp false** | 末 stage 8.25261 |
| hsdp | dp_replicate=2 × dp_shard=2（4 rank） | 9.92072 |

PP 下只有**最后一个 stage** 记真实 loss，其余 stage 记 `-1` 哨兵；
但 `grad_norm` 全 rank 相同（PP mesh 上做了同步裁剪）。

### 边界结论（修正之前的判断）
- **CP 是唯一硬阻塞**（CPU SDPA 派发到
  `_scaled_dot_product_flash_attention_for_cpu`，无 DTensor 分片策略）。
  故 **PP×TP×FSDP×CP 四维组合在本机不可达**；去掉 CP 的三维组合已验证可跑。
- **hsdp 不是「结构性」不可用**：4 rank（2×2）可用，8 rank（2×4）挂。
  已排除线程超订（`--threads 1` 也挂）与启动争抢（`--stagger 8` 也挂）；
  本机正好 8 核。纯 replicate（2×1）可用。
- **`pp_tp_fsdp` 的阻塞点是 SP 而非三维并行**：SP 关闭即通。
